# 交互设计

启用时简要说明正在使用“交互设计”。目标是让已请求的交互完整，而不是增加功能数量。

## 形成可执行的交互方案

- 从用户原文、已确认对话和本轮实际可用上下文中，提取用户要完成的操作。区分已明确要求、仍需确认的业务选择和实现细节。
- 用简短的“当前状态 → 用户动作 → 内容与状态变化 → 完成或退出”描述交互；涉及多个控件时，明确共享状态及其更新关系。不需要向用户展示程序状态机或内部推理。
- 存在会改变业务含义、操作结果或布局范围的歧义时，沿用平台澄清流程，只问当前关键问题。不要为每个实现细节都追问，也不能把常见设计习惯写成已确认业务规则。
- 对多状态或联动任务，按需读取 `references/state-transitions.md`，仅选择任务相关的检查项。不为简单任务加载完整清单。

## 咨询与实际修改

纯方案咨询只给方案，不声称已读取或修改页面。缺少页面上下文时，说明建议基于用户描述。

实际编辑时，将已确定的交互纳入现有 `declare_intent`，不要另做一轮重复计划。已有足够上下文就执行，不为寻找更优方案反复搜索；组件、布局和样式选择遵循平台规则与当前页面证据，不假设固定 DOM 层级、布局或容器尺寸。

只实现用户要求的本地 UI 示意。涉及真实数据写入、检索、权限或通知时，遵循平台能力边界，不能用模拟成功掩盖未接入服务。未要求的审核流程、导出、权限管理等不顺带增加。

完成前对照已声明的状态转换检查源码是否覆盖请求；编译和源码检查不等于实际渲染或交互验证，不增加自动浏览器重试闭环。最终只说明已提交的改动、使用方式及影响预期的限制。
