# 需求交付

启用时说明正在使用“需求交付”。整理评审或研发可用的材料，不自动修改页面或承诺真实业务已经实现。

## 按本轮交付目的选择材料

先根据用户原文确定是在整理需求，还是报告已经完成的修改；技能名称不替代原文中的目标和验收要求。

- 整理需求草稿：以用户提供的目标、约束和验收要求为材料。材料足够时直接生成，不为填充“当前页面”“修改记录”“未实现项”而读取源码。缺少实现证据不妨碍记录需求，也不代表尚未实现。短需求只需相关的目标、要求与待验证验收项；没有必要的缺口就不添加待确认清单。
- 整理修改成果：按用户要求的范围核对实际可读记录；需要确认当前源码时才定向读取。不把需求草稿自动扩展为交付验收报告，也不把参考材料中的全部章节视为必填项。

## 先确定材料能证明什么

聊天可使用传入的用户消息、最近对话和轻量选区信息；平台提供副本只读工具时，还可以按需核对本轮绑定版本的已保存源码。只有实际读取过的材料才能作为证据，局部摘要不代表完整页面。仍没有版本差异、全部历史或浏览器实时状态的工具。对话可能被截断，副本也可能在本轮读取版本之后继续变化；若用户要求全量交付而材料不足，说明本次覆盖范围，请求补充缺失材料，不编造历史。

区分以下证据：

- 用户明确提出或确认的内容：作为需求依据，不等于已实现。
- 历史助手的完成说明：写为“对话记录报告的修改，当前版本待核对”，不能据此标记验收通过。
- 本轮实际拿到的工具结果：仅支持结果明确证明的事实；源码提交或编译通过不证明视觉、交互验收通过。
- 用户实际验证反馈：注明“用户反馈已确认”及其具体范围，不扩大到整个页面。

未知规则、未覆盖交互和缺失证据保留为待确认或待验证。未接真实接口、仅使用演示数据等限制，应放进交付边界，不埋在技术细节里。

“没有读到”“工具省略了”“没有修改记录”都不能证明功能、样式或实现不存在。只有明确的用户说明或实际证据支持时才列为未实现；否则写为实现状态未核对。资料未覆盖的内容不做数量或存在性断言。

## 组织交付说明

按用户所需详细程度选择章节：目标与范围、需求依据、交互流程、记录中的修改、验收清单、未实现及待确认事项。短需求不必凑齐空章节。

整理修改成果和验收清单时读取 `references/handoff.md`，根据实际材料生成内容。不要要求用户提供源码标识；不把工具流水账当成产品交付说明。

用户只要求讨论交付方案时直接回答。要求生成文档时复用现有渲染脚本：Python 可用时使用 `scripts/render.py`，否则使用等价的 `scripts/render.mjs`，只运行一个。脚本只排版，不核实页面状态；输入内容的证据分级由你负责。

args 格式如下，inputs 可为空：

```json
{"title":"需求交付说明","sections":[{"heading":"范围与依据","items":["根据本次用户确认内容整理，仅覆盖当前可读对话"]},{"heading":"验收清单","items":["待验证：前置状态、用户操作及可观察的预期结果"]}]}
```

脚本成功返回 `requirements.md` 后，在回答中展示正文。失败时如实说明，可提供标注“未通过脚本生成”的文本草稿，不伪造脚本产物。当前不提供下载链接，不暴露服务器临时路径。生成交付文档不等于页面修改或验收已完成。
