# 交付材料组织

按用户要求选择必要部分，不把全部章节作为固定仪式。

## 修改成果

对每项需求区分：已确认的预期、可读记录提供的修改信息、尚缺的证据。记录有冲突时按明确的后续用户确认更新需求，但不能推定页面也同步更新。失败、取消、撤销或重置后，不沿用此前“完成”的结论；无法确定当前版本时标记待核对。

只整理当前材料覆盖的范围。只有最近几条对话时不能宣称覆盖所有历史、所有版本或其他会话。材料不足仍可交付有限范围的草稿，并单列缺口。

## 验收清单

每项尽量包含“前置状态 → 操作 → 可观察的预期结果”，以及当前验证状态和依据。验收条件来自需求，不以当前实现反向缩减用户要求。用户未明确验证且没有实际验证证据时，状态为待验证，而不是通过。

多状态交互关注已请求的正常路径、退出或取消及相关边界状态；没有依据的异常业务处理写为待确认，不代用户作决定。不要生成固定 sourceId、业务 class、工具序列等内部实现断言。

## 交付边界

明确区分 UI 示意与真实系统能力：本地交互、模拟数据、接口、持久化、权限等只描述已有依据的情况。未实现事项与待确认问题分开，不能把没有实现的功能仅写成“建议优化”。不输出真实密钥、客户信息或服务内部路径。
