# 从原网页到静态副本：技术实现详解

## 1. 定位

本方案不是简单复制网页，也不是截取一张页面图片，而是将用户当前看到的运行态网页编译为一份安全、可维护、可由 Agent 持续编辑的静态源码副本。

静态副本仅服务于页面需求示意与协作编辑，不承载真实业务接口、表单提交、跨页面流程或原页面 JavaScript 逻辑。

```text
浏览器运行态页面
  → 页面采集
  → 状态冻结
  → 安全清洗
  → HTML/CSS 规范化
  → 元素索引与源码映射
  → 静态源码工作区
  → 隔离预览与 Agent 编辑
```

## 2. 为什么不能直接复制 DOM

直接读取 `document.documentElement.outerHTML` 不能形成可靠的编辑副本，主要原因包括：

- 用户当前看到的弹窗、下拉框、输入内容和选中状态可能来自 JavaScript 运行后的内存状态，初始 HTML 中并不存在；
- 页面保留脚本、事件、接口、表单提交和跳转能力，不符合静态需求示意的安全边界；
- React、Vue 等框架可能重新渲染，直接修改运行态 DOM 容易被覆盖；
- DOM 中通常存在动态类名、临时属性和冗余结构，不适合作为 Agent 的长期编辑对象；
- 仅复制 DOM 无法自然解决样式、资源、版本、撤销重做和多轮编辑问题。

因此，静态副本的目标是：保留用户创建副本时的主要视觉和结构状态，移除业务执行能力，并将页面转换为可检索、可验证、可版本化的 HTML/CSS 工作区。

## 3. 页面采集

### 3.1 采集对象

采集发生在浏览器 Content Script 中，面向已经完成渲染的当前 `document`，而非服务器返回的初始响应。

主要采集内容包括：

- 当前 DOM 结构；
- 元素属性与可见文本；
- 输入框、文本域和选择控件当前值；
- 单选、多选和开关状态；
- 当前显示或展开的区域；
- 已打开弹窗与遮罩；
- 主要计算样式；
- 当前页面、视口和元素几何信息。

### 3.2 使用运行态而非初始源码的原因

业务页面中的数据、组件状态和弹窗通常在 JavaScript 执行后才生成。只保存初始 HTML 时，副本往往无法反映用户实际看到的页面。

因此，系统以浏览器最终渲染结果作为快照输入，使副本能够尽量保留当前表单值、展示状态和视觉布局。

### 3.3 样式采集

页面最终样式通常由全局样式、组件库、CSS Modules、行内样式、继承、层叠和媒体查询共同决定。仅复制原始样式文件，通常不足以还原当前视觉效果。

采集阶段读取元素主要计算样式，并在后续编译阶段归并与去重，生成可独立预览的 `snapshot.css`。

## 4. 状态冻结

浏览器控件的真实状态不一定体现在 HTML 属性中。例如，用户填写输入框后，`input.value` 已经变化，但 HTML 中的 `value` 属性仍可能保留初始值。

因此，需要将运行态状态写回静态结构：

- `input.value` 写入 `value`；
- `textarea.value` 写入节点文本；
- `checkbox`、`radio` 的 `checked` 状态写回属性；
- `option.selected` 写回 `selected`；
- 当前展开或隐藏状态固化为结构和样式；
- 已打开弹窗与遮罩作为静态节点保留。

冻结后的副本只表示创建时刻的页面状态，不继续执行原页面业务状态机。

## 5. 安全清洗

### 5.1 编译阶段清洗

静态副本不应拥有业务页面的可执行能力。编译阶段移除或禁用：

- `script`、`iframe`；
- `onclick`、`onchange` 等内联事件属性；
- 表单 `action` 和真实提交行为；
- `javascript:` 等危险协议；
- 页面跳转和真实业务接口；
- Cookie、LocalStorage、SessionStorage 等运行态存储；
- React/Vue 运行时标记和无关临时属性；
- 不受控外部资源与危险内容。

### 5.2 预览阶段隔离

预览页通过 Content Security Policy 形成第二层安全边界，限制：

- 脚本执行；
- 接口请求；
- 表单提交；
- 页面导航；
- 不受控外部资源加载。

原页面始终保持只读。Agent 修改的是静态 Workspace 中的 HTML/CSS 文件，不能操作原业务页面或调用原业务接口。

## 6. HTML/CSS 规范化

### 6.1 规范化目的

直接序列化的 DOM 通常包含大量单行内联样式、动态类名、临时属性和冗余结构，不利于模型检索、局部读取和安全 Patch。

因此，服务端将副本整理为：

```text
index.html      格式化后的页面结构
snapshot.css    提取、归并后的页面可见样式
```

### 6.2 主要处理

规范化过程包含：

- HTML 格式化；
- 主要可见样式提取；
- 重复 CSS 声明去重；
- 资源引用规范化；
- 稳定元素标识注入；
- 无效或危险属性删除；
- 页面元信息补充。

拆分结构和样式后，Agent 可以按需读取局部 HTML，或者读取某个组件的完整样式规则，而不需要在整页混杂源码中定位。

## 7. 稳定元素标识与源码映射

### 7.1 `sourceId`

副本中的可编辑元素会带稳定标识，例如：

```html
<button data-ui-source-id="el-abc123">提交订单</button>
```

该标识贯穿：

- 副本预览页；
- 用户当前选区；
- 页面 Outline；
- Source Map；
- Agent 工具调用；
- Revision 和日志。

用户点选页面元素后，插件传递稳定 `sourceId`。Agent 据此定位目标结构、父容器、相邻元素和关联样式，而不是依赖容易变化的 CSS Selector。

### 7.2 页面 Outline

`outline.json` 是面向 Agent 的页面目录，包含：

- 主要页面区域；
- 容器层级；
- 元素类型和可见文本；
- 稳定 `sourceId`；
- 关键属性；
- 局部父子关系。

Agent 首先读取 Outline 获取整体页面结构，再按需定位和读取局部源码。

### 7.3 Source Map

`source-map.json` 记录元素与源码的对应关系：

```text
sourceId
  → HTML 节点及源码位置
  → 关联 CSS 规则
  → 父容器与相邻元素
  → 几何与可见性信息
```

例如，用户提出“在订单状态右侧增加筛选项”时，Agent 可以先从 Outline 定位“订单状态”，再读取其容器、相邻组件和关联样式，而不是将整页 DOM 放入模型上下文。

## 8. 资源处理

图片、字体、SVG、背景图和 CSS `url()` 的来源可能是相对路径、绝对 URL、内联 Base64、跨域 CDN 或需登录态访问的资源。

当前处理原则如下：

1. 可安全获取且允许保存的资源，转存或内联到副本；
2. 可访问但不适合下载的资源，按限制性策略保留；
3. 跨域受限、无法访问或存在安全风险的资源，替换为占位；
4. 记录资源降级信息，避免静默失真。

这也是跨设备导入后可能出现字体、居中、换行或尺寸偏差的主要原因：快照结构可以完整保留，但目标环境的字体、资源和视口条件不一定一致。

## 9. 静态源码工作区

每个页面副本对应一个独立 Workspace。典型目录结构如下：

```text
workspace/
├── index.html        页面结构
├── snapshot.css      页面样式
├── outline.json      页面区域、元素和层级摘要
├── source-map.json   页面元素与源码位置映射
├── workspace.json    工作区、选区、会话和版本信息
└── revisions/        历史版本快照
```

本地调试时，默认目录为：

```text
apps/agent-service/.snapshots/source-workspaces/{workspaceId}/
```

可使用以下环境变量覆盖默认目录：

```env
SOURCE_WORKSPACE_DIR=/custom/path/source-workspaces
```

容器部署时，默认目录为：

```text
/data/source-workspaces
```

## 10. Working Copy 与 Revision

每次 Agent 编辑均在 Working Copy 中执行，而不是直接覆盖当前有效页面：

```text
当前 Revision
  → 创建 Working Copy
  → Agent 搜索、读取、编辑 HTML/CSS
  → 结构、安全、空间校验
  → 通过后提交新 Revision
  → 失败则丢弃 Working Copy
```

Revision 保存当时的源码、版本说明和会话关联信息，支持：

- 撤销、重做；
- 恢复初始副本；
- 查看历史页面状态；
- 导出当前页面截图；
- 追溯每次修改的 Agent 工具轨迹。

撤销时不仅恢复 `index.html` 和 `snapshot.css`，还会同步截断对应的后续对话上下文。否则模型可能继续引用已经撤销或删除的元素，导致页面状态与模型记忆不一致。

## 11. 与 Agent 的协作方式

静态副本将网页转化为可检索的文件工作区。Agent 不需要一开始读取整页 HTML/CSS，而是采用渐进式上下文：

```text
用户需求 + 当前选区 + 页面 Outline
  → 搜索目标元素
  → 读取局部 HTML/CSS 与样式规则
  → 执行受控编辑
  → 校验并提交 Revision
```

例如，“在右侧增加一个与现有控件样式一致的筛选项”可拆解为：

1. 定位当前选区和相邻组件；
2. 读取共同父容器及实际布局方式；
3. 读取待复用组件的完整结构和样式规则；
4. 插入或克隆组件结构；
5. 修改文案、选项和属性；
6. 校验新增内容的结构、样式和空间归属；
7. 提交新 Revision。

系统工具以搜索、读取、替换、插入、移动、克隆、删除、重排、Patch、校验和提交等通用原语组成，不为“订单”“筛选项”等具体业务概念固化专用工具。

## 12. 当前能力边界

当前目标是高保真静态需求示意，不是浏览器级完整复刻。以下能力会被有意裁剪或降级：

- 原页面 JavaScript；
- 接口请求和真实业务提交；
- 跨页面业务流程；
- 复杂动画；
- Canvas、视频；
- 完整响应式状态机；
- 所有跨域字体和资源；
- 像素级跨设备一致性。

静态副本的核心价值不在于保留所有业务能力，而在于把运行中的网页统一沉淀为安全、稳定、可版本化、可由 Agent 持续编辑的页面资产。

## 13. 后续技术方向

1. **真实浏览器验证：** 在静态校验后增加浏览器几何检测，检查位置、重叠、裁切、溢出、可见性和样式一致性。
2. **资源本地化：** 完善图片、字体和 CSS 资源的安全缓存与跨设备还原能力。
3. **跨视口一致性：** 记录并约束快照视口，减少响应式规则造成的布局漂移。
4. **企业组件接入：** 将企业组件库、视觉 Token 和设计规范转化为可检索的页面约束。
5. **需求资产关联：** 将定稿 Revision 与需求文档、特性、评审意见和研发任务建立版本关系。
