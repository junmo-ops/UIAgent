# 《AI+研发协同 UI 需求示意助手》比赛配图生成提示词

本文档对应当前比赛作品提交稿中的图 1～图 6。提示词可以直接复制给图片生成工具使用。

## 使用建议

- 图 1、图 2、图 3 适合使用 AI 生成信息图，建议统一使用 16:9 横版、白色背景、蓝紫色科技感配色。
- 图 4、图 5、图 6 涉及真实产品能力，优先使用项目实际截图，再用 Figma、PPT 或图片编辑工具排版。AI 生成的界面文字容易出现错别字，不建议直接作为最终证据截图。
- 如果图片生成工具无法稳定生成中文文字，可以要求它保留清晰的文字框、标题框和按钮形状，之后人工叠加中文标签。
- 所有图片都不要出现真实客户名称、真实账号、Cookie、Token、API Key、内部域名或敏感业务数据，统一使用脱敏示例。

## 图 1：传统需求沟通与 AI 示意流程对比

用途：说明项目解决的核心痛点，突出从“文字反复沟通”到“页面副本直接生成示意”的变化。

建议尺寸：16:9 横版，适合放在“核心痛点/项目目标”章节。

提示词：

```text
请生成一张企业产品设计流程对比信息图，16:9 横版，白色背景，简洁高级的蓝紫色科技风，中文标签清晰易读，左侧和右侧形成明显对比，中间用箭头连接。

左侧标题为“传统方式”，展示产品经理、文字需求、研发工程师、反复沟通、修改原型等节点：产品经理只能用文字描述页面改动，研发看不清位置和交互，双方通过多轮沟通确认，最后才得到一个页面示意。用多个来回箭头表现沟通成本高、流程长。

右侧标题为“使用 UI 需求示意助手”，展示真实页面、选择页面区域、自然语言描述、AI 生成静态 UI 示意、导出截图、研发快速理解等节点：产品经理在页面副本中选中区域并描述“在右侧增加筛选项”，系统生成接近原页面风格的 UI 示意，产品经理导出截图交给研发。用一条清晰的顺序箭头表现流程更短。

右侧强调三个结果标签：“复用真实页面”“减少反复确认”“快速形成可评审示意”。整体风格专业、克制、适合企业技术比赛方案书，不要出现夸张机器人、科幻城市或营销海报元素。
```

反向提示词：

```text
不要手机界面，不要游戏风格，不要真人大头像，不要复杂背景，不要虚构公司 Logo，不要真实姓名和敏感数据，不要密集难以阅读的小字，不要把左右两侧流程混在一起。
```

## 图 2：页面快照到交付的闭环流程

用途：说明系统的端到端工作方式。

建议尺寸：16:9 横版，流程节点 6～7 个，适合放在“总体思路/核心操作流程”章节。

提示词：

```text
请生成一张软件系统端到端流程图，16:9 横版，白色背景，蓝紫色和青绿色作为强调色，扁平化企业 SaaS 信息图风格，节点排列清晰，中文标题可读。

从左到右依次展示 7 个步骤，并用粗细适中的箭头连接：
1. “原业务页面”：浏览器中一个企业后台页面，包含表格、筛选项和弹窗；
2. “捕获运行态页面”：插件读取当前可见页面、表单值、勾选状态和已打开弹窗；
3. “安全裁剪”：移除脚本、事件、接口、表单提交和远程资源，旁边用锁和剪刀图标表示；
4. “静态源码工作区”：展示 index.html、snapshot.css、outline.json、source-map.json 四个文件卡片；
5. “源码 Agent”：AI Agent 通过搜索、局部读取和受控 Patch 修改 HTML/CSS；
6. “校验与预览”：展示安全校验、空间校验、Revision 版本和静态副本预览；
7. “交付”：展示导出截图、导出快照包和研发评审。

在流程底部增加一条横向安全边界说明：“原业务页面只读｜不执行脚本｜不调用真实接口｜修改只发生在隔离静态副本”。整体要突出闭环、隔离和可追溯，不要出现代码堆砌或复杂 UML 符号。
```

## 图 3：分层技术架构图

用途：展示系统分层、组件边界和数据流，适合放在“技术架构”章节。

建议尺寸：16:9 横版；如果文字较多，可使用 4:3 横版并后期排版。

提示词：

```text
请生成一张专业的软件系统分层架构图，16:9 横版，白色背景，中文文字清晰，采用自上而下的分层布局，使用蓝色、紫色、青绿色区分不同层级，风格类似企业技术方案架构图，简洁、规整、可打印。

从上到下展示以下层级，并用双向箭头表示调用关系：

第一层“浏览器插件层”：Chrome MV3、Side Panel、Background、Content Script；
第二层“快照捕获与编译层”：运行态页面采集、表单与弹窗状态冻结、安全裁剪、HTML/CSS 规范化、Outline、Source Map；
第三层“Agent Service 层”：Hono HTTP API、DeepSeek/OpenAI-compatible 模型适配、Cline Agent Adapter、上下文管理和实时进度；
第四层“受控源码编辑层”：list/search/read、inspect、replace、apply_patch、move、clone、validate、finish；
第五层“Workspace 与安全层”：静态文件、Revision、撤销重做、快照包、路径隔离、危险内容校验、CSP、体积限制；
第六层“交付与观测层”：静态副本预览、截图导出、日志页、JSONL 日志、自动化测试和挑战场景评测。

右侧增加“模型不可直接访问”的边界说明，左侧增加“原页面只读”的安全边界。图中不要画数据库、真实业务接口或任意脚本执行模块，突出通用 Agent 能力与 UI 需求业务能力之间的边界。
```

## 图 4：插件 Side Panel 与进入副本编辑

用途：展示用户如何从真实页面进入隔离副本。

建议尺寸：4:3 或 16:10。

截图采集建议：使用真实业务页面截图、插件 Side Panel 截图和“进入副本编辑”确认状态截图，按“打开插件 → 确认进入副本 → 打开静态副本”三步横向拼接，并用 1、2、3 标注。不要使用 AI 生成，避免界面文字和真实交互状态失真。

## 图 5：复杂需求前后对比

用途：展示 Agent 如何围绕选区完成复杂 UI 改动，并保持原页面的视觉语言。

建议尺寸：16:9 横版，优先使用真实修改前后截图；可以在截图上加选区框、指令气泡和结果标注。

推荐做法：左侧放“修改前”，中间放用户指令，右侧放“修改后”，底部放 Revision、撤销和重做状态。

截图采集建议：使用同一真实页面的修改前、选区状态、修改后截图，三栏排列。中间叠加真实用户指令，右侧用标注框突出新增区域，底部补充真实 Revision、撤销或重做记录。不要用 AI 重新绘制页面，以免样式细节失真。

## 图 6：Agent 实时进度与日志页

用途：展示系统不是黑盒，用户可以看到 Agent 当前阶段、模型调用次数、工具调用次数、耗时和错误原因。

建议尺寸：16:9 横版，最好使用项目真实日志页截图，再用标注框突出关键区域。

截图采集建议：直接截取项目的 Agent 进度界面和日志页面。建议至少包含进度时间线、模型调用次数、工具调用次数、耗时、最终状态和一条脱敏 JSONL 日志。可用红框标出一次失败原因或用绿色标出成功提交 Revision。不要使用 AI 生成，日志数据必须来自真实运行记录并脱敏。

## 建议的图片统一风格

如果希望 6 张图在提交材料中看起来统一，可以在每张提示词末尾追加：

```text
统一采用企业技术比赛作品集风格：白色背景、浅灰卡片、深灰正文、蓝紫色主色、少量青绿色成功状态，圆角矩形和细线箭头，留白充足，信息层级清晰，避免炫酷渐变和复杂装饰，适合插入 A4 方案书，所有中文文字清晰可读。
```

## 最终交付前检查

- 图 1～图 3：检查流程方向、分层关系和安全边界是否准确。
- 图 4～图 6：优先替换为真实项目截图，AI 生成图只作为版式或概念示意。
- 所有图片：检查是否误出现真实域名、账号、Token、Cookie、内部系统名称和未脱敏业务数据。
- 图片说明文字要与比赛正文一致，不要把“静态副本”写成“修改生产页面”，不要把“模型调用”写成“模型直接操作浏览器”。
