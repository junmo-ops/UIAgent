# UI 辅助需求编写插件：静态快照体积优化需求与方案

## 1. 需求背景

UI 需求助手会把当前运行态页面冻结为一个可编辑的静态副本。这个副本是后续源码编辑、预览、撤销、导出和审计的基础，因此不能以“只保留当前屏幕”作为默认策略：用户进入副本后仍可能要选择页面其他区域继续编辑。

当前快照采集会为大量元素写入完整的计算样式。企业页面中重复使用的按钮、表单项、表格单元格和布局容器很多，即使视觉上相同，也会在 HTML 中重复保存同一组 CSS 声明；当页面节点较多时，快照可能超过原有 10 MB 校验上限。将上限提高到 30 MB 能避免立即失败，但并不解决传输、存储、检索噪声和后续模型理解成本过高的问题。

本需求要建立一套可观测、可解释、可按需降级的通用快照优化能力，而不是针对某个站点、某类弹窗或某条需求做裁剪规则。

## 2. 目标

1. 在不改变静态副本页面语义、可编辑范围、节点结构和运行态冻结结果的前提下，显著降低快照传输与存储体积。
2. 让系统可以说明“快照为什么大”，区分 DOM、重复样式、伪元素样式和内嵌资源等来源，而不是只在超限后返回笼统错误。
3. 将完整页面保留为默认能力；只有无损优化后仍超出安全阈值，才由用户显式选择更小的捕获范围。
4. 降低 Agent 读取工作区时的无效重复信息，提升复杂页面的检索与编辑稳定性。

## 3. 非目标与边界

- 不执行原页面脚本，不恢复接口、路由、真实表单提交或跨页面流程。
- 不按业务 URL、页面文案、固定 class、组件名称或 DOM 层级编写特例。
- 不在用户无感的情况下删除不可见节点、弹窗、抽屉、表格分页内容或选区外内容。
- 不以压缩字符串替代可维护源码；Agent 仍需得到可读的 `index.html` 与 `snapshot.css`。
- 不承诺完整还原 Canvas、视频、跨域字体、远程背景图或复杂运行时动画。
- 本期不把“减小快照”误等同于“把完整 HTML 直接塞进模型上下文”。源码 Agent 应继续通过目录、结构索引和局部文件读取工具按需获取内容；本需求优化的是上传、工作区、索引和局部读取时的有效信息密度。

## 4. 核心原则

### 4.1 先无损，后有损

第一优先级是消除表示层重复：同一套计算样式只保存一次，并由多个节点引用。DOM、文本、属性、控件值、选中状态、展开状态、有效的 `data:` 资源和可编辑范围均保持不变。

只有无损优化仍无法满足安全阈值时，系统才提供捕获范围选择。范围缩小属于用户可见的产品决策，不应由采集器静默执行。

### 4.2 先度量，后设阈值

不能仅凭“HTML 超过 10 MB”决定如何裁剪。必须记录快照构成、无损优化收益和超限原因，再根据真实页面样本确定告警线、上限和降级策略。

### 4.3 采集、编译、Agent 分层

采集端负责安全冻结和无损去重；工作区编译器负责把快照整理为稳定、可读的源码；Agent 只按需读取工作区局部内容。三层均不依赖特定业务页面。

## 5. 方案概览

```text
运行态页面
  → 安全冻结与运行态复制
  → 快照体积分析
  → 无损样式规范化与去重
  → 生成 StaticSnapshot（HTML + 内嵌基础样式）
  → 服务端校验与工作区编译
  → index.html + snapshot.css + outline.json + source-map.json
  → Agent 按结构索引和局部文件读取、编辑

若仍超限
  → 展示体积原因与可选捕获范围
  → 用户确认后重新采集
```

## 6. 第一阶段：快照分析与无损样式去重

### 6.1 快照诊断指标

在插件采集完成、服务端入库前记录以下结构化指标。指标写入请求日志和工作区元数据，不默认发送给模型；模型只有在确实需要排查快照质量时，才可通过受控工具读取摘要。

- `nodeCount`：有效元素节点数。
- `rawDomChars`：清理后但未写入计算样式的 DOM 字符数。
- `inlineStyleCharsBefore`：逐节点内联计算样式的总字符数。
- `uniqueStyleRuleCount`：去重后的唯一样式规则数。
- `uniqueStyleChars`：唯一样式规则总字符数。
- `styleDedupSavedChars`：样式去重节省的字符数与比例。
- `pseudoStyleChars`：`::before`、`::after` 规则字符数。
- `inlineDataResourceChars`：安全保留的 `data:image`、`data:font` 等内嵌资源字符数。
- `serializedHtmlCharsBefore`、`serializedHtmlCharsAfter`：优化前后的完整快照大小。
- `optimizationVersion`：规范化算法版本，便于回归比对和后续兼容。

这些指标使错误提示能够区分“节点过多”“重复样式占比高”“内嵌资源过大”等不同情形。

### 6.2 无损样式规范化

当前采集器已按固定属性列表读取计算样式，工作区编译器也会把相同内联样式转成 `ui-snapshot-style-N` 类。优化后将这一步前移到采集端，避免同一组声明先在网络中重复传输、再在服务端去重。

处理规则：

1. 对每个元素生成稳定的样式指纹：属性顺序固定、值经过既有规范化、忽略不安全的 `url()` 值。
2. 相同指纹只生成一条捕获样式规则，例如 `.ui-captured-style-12{...}`；节点仅增加对应 class，不再重复写入完整 `style` 属性。
3. 去重后的规则写入快照 `<style>` 中，连同伪元素规则一起作为快照基础样式提交。
4. 保留元素原有 class、`data-ui-source-id`、运行态值、选中状态、可见尺寸信息和文本内容；生成的 class 使用独立命名空间，避免与原页面 class 冲突。
5. 服务端编译器继续将基础样式输出到 `snapshot.css`，并保持 `index.html` 可读、可定位、可编辑。兼容旧快照中仍存在的内联样式。

该方案只改变“相同样式如何存储”，不会通过推断隐藏元素或重排节点来换取体积。

### 6.3 安全与一致性校验

无损去重上线前，需要在采集后校验以下不变量：

- 去重前后元素数、`data-ui-source-id` 集合、文本内容、关键表单状态和安全属性清理结果一致。
- 同一页面重复采集时，样式指纹与规则编号顺序稳定，避免无意义的版本差异。
- 快照中不存在 `script`、事件属性、远程 URL、`@import` 或被禁止的活动内容。
- 编译后的工作区仍能建立完整 `outline.json` 与 `source-map.json`，每个可定位元素都可回溯到 `index.html`。
- 采用普通流、Flex、Grid、定位容器、滚动区域等不同页面形态进行真实浏览器对比，不仅验证单一业务页面。

## 7. 第二阶段：超限后的显式范围降级

### 7.1 触发条件

先完成无损去重并重新计算体积。仅当结果仍超过协议安全阈值、服务端配置阈值或工作区处理预算时，进入降级引导；正常页面不展示额外选择，默认保留完整当前页面。

### 7.2 用户可选范围

系统展示实际体积、主要占比和各方案预计大小，由用户选择后重新采集：

1. **完整当前页面（默认）**：保留 `body` 已渲染内容，适合需要在不同区域持续编辑的场景。
2. **当前可见范围**：保留当前浏览器视口及必要的结构上下文，适合只做当前屏幕示意。
3. **选择区域及结构上下文**：用户先选定目标区域，再保留其本身、必要祖先容器和与布局相关的相邻结构。具体上下文边界由页面结构和模型/规则化布局分析共同确定，不能用固定祖先层数替代。

三个选项都必须在界面中说明：缩小范围后，副本仅可编辑被捕获内容；未捕获区域不会在副本中出现。

### 7.3 不采用的方案

- 自动仅保留可视节点：会丢失用户刚好未滚动到的编辑目标。
- 自动删除 `display:none` 或透明节点：隐藏内容可能是弹窗、Tab、展开状态或后续需展示的 UI。
- 通过自然语言关键词猜测“用户只想改顶部/底部”：属于不可泛化的业务启发式。
- 把完整 HTML gzip 后直接给 Agent：传输可压缩，但 Agent 无法直接阅读和编辑压缩内容，不能解决源码可维护性与检索质量。

## 8. 阈值与失败处理

### 8.1 分层阈值

阈值不再只使用单一 HTML 字符数，而是分层管理：

- **提示阈值**：达到后记录提示与诊断信息，但仍允许完整快照继续。
- **优化后告警阈值**：无损去重收益低或仍然偏大时，建议用户选择范围。
- **硬性拒绝阈值**：超过服务端接收、磁盘配额或安全预算时，不创建工作区，并明确返回原因与可选范围。

初始数值以当前 30 MB 静态 HTML 硬限制为安全兜底；提示与告警阈值应在收集一批真实页面的诊断数据后配置，不在本需求中凭经验写死。

### 8.2 失败提示示例

```text
当前页面的静态副本优化后仍为 34.2 MB，超过 30 MB 安全限制。
主要来源：内嵌资源 18.6 MB、唯一样式 9.7 MB、DOM 5.9 MB。

你可以选择“当前可见范围”或“选择区域及结构上下文”后重新创建副本；
未捕获的区域不会出现在副本中。
```

错误信息必须基于诊断数据生成，不能只显示“HTML 太大”。

## 9. Agent 上下文策略

快照体积与模型输入量相关，但不是一一对应关系。正式策略如下：

1. Agent 不接收完整快照文本作为每轮固定提示词。
2. Agent 先读取 `outline.json`、`source-map.json` 和当前选区摘要，再按需读取 `index.html`、`snapshot.css` 的相关片段。
3. 诊断指标仅作为工作区健康信息，默认不进入普通编辑轮次。
4. 当局部文件仍然很大时，优先扩展结构化检索、分段读取和引用定位能力，而不是截断用户未授权删除的源码。

因此，本需求通过减少重复样式、提高源码可读性和增强局部检索，降低有效上下文负担；它不以牺牲页面范围为默认代价。

## 10. 快照结构化与模块化工作区

### 10.1 目标

体积优化解决“静态页面过大”，但不能单独解决复杂页面的源码理解问题。当前工作区以
`index.html`、`snapshot.css`、`outline.json`、`source-map.json` 为主；当页面包含多个
筛选区、表格、表单、抽屉或弹窗时，即使 Agent 按片段读取，也难以快速建立模块边界和
影响范围。

因此，工作区需要在完整页面源码之上提供一层可追溯的逻辑模块索引。模块的目的不是模仿
React/Vue 组件，也不是依赖业务组件名称，而是把当前已渲染页面中可独立理解、定位和编辑的
结构区域表达给 Agent。

### 10.2 目标工作区形态

```text
workspace/
├── page/
│   └── index.html                 # 当前唯一真实页面源码
├── styles/
│   ├── snapshot-base.css           # 冻结后的基础样式
│   └── generated.css               # 后续编辑生成的样式
├── maps/
│   ├── outline.json                # 全量 DOM 结构索引
│   ├── source-map.json             # sourceId 到源码位置映射
│   └── module-map.json             # sourceId 到逻辑模块映射
├── modules/
│   └── {moduleId}/
│       └── module.json             # 模块摘要与可读视图元数据
├── workspace.json
└── revisions/
```

首期的 `modules/` 是逻辑目录，不是把完整 HTML 立即物理拆成多个可直接运行的片段。
`page/index.html` 仍是唯一可写入、可编译和可预览的事实来源；模块目录提供 Agent 的受控
阅读入口与定位信息，所有补丁仍通过 `source-map.json` 精确回写到真实源码。

### 10.3 模块元数据

模块由通用结构、布局和可见性信息生成，不使用页面 URL、文案、固定 class 或特定 DOM 层数。
每个模块至少包含：

- `moduleId`、根 `sourceId`、父模块与子模块关系；
- 标签、可访问性角色、结构摘要和文本摘要；
- 捕获时的几何范围与可见状态；
- 对应 HTML 范围、相关样式类和外部样式依赖；
- 与当前选区的包含、相邻或重叠关系；
- 基于结构事实生成的模块类型，例如内容区域、表单区域、列表区域、浮层区域或普通容器。

示例：

```json
{
  "moduleId": "module-source-48",
  "rootSourceId": "source-48",
  "kind": "content-region",
  "summary": "包含列表标题、表头、数据行与分页的内容区域",
  "sourceRange": { "file": "page/index.html", "startLine": 120, "endLine": 468 },
  "dependencies": ["styles/snapshot-base.css"],
  "bounds": { "x": 24, "y": 240, "width": 1200, "height": 680 }
}
```

`kind` 仅作为检索和摘要辅助，不能成为固定布局决策依据；Agent 在修改前仍需读取真实模块结构和
相关样式，必要时向用户澄清。

### 10.4 Agent 的模块化读取与编辑流程

```text
用户选中页面区域
  → sourceId 查询 source-map 与 module-map
  → 获得当前模块、父模块、相邻模块和关联样式摘要
  → Agent 按需读取该模块的 HTML/CSS 片段
  → 生成受控补丁并回写 page/index.html 或 styles/generated.css
  → 重新生成 outline、source-map、module-map
  → 静态预览渲染与通用校验
```

这样，普通局部编辑不需要先读取整页源码；跨模块需求则由 Agent 显式扩大读取范围，而不是依赖
隐式的全文注入。模块索引也应进入 Revision：每次成功修改后重新生成，撤销或重做时随对应源码
版本恢复，避免索引与页面不一致。

### 10.5 为什么先逻辑模块化，不直接物理拆文件

将任意网页直接拆成多个 HTML 文件会遇到 CSS 层叠、跨模块选择器、继承、绝对定位、表格结构和
DOM 顺序等问题；在不执行原页面 JavaScript 的静态副本中，这会显著提高预览失真风险。

因此采用两阶段演进：

1. **逻辑模块化**：完整 HTML 保持唯一事实来源，生成模块索引和虚拟阅读视图。优先提升 Agent
   定位精度与上下文效率，不改变页面渲染模型。
2. **物理模块化（后续）**：仅在模块边界、样式依赖分析和工作区编译器均经过验证后，再把满足条件
   的模块抽取为独立 HTML/CSS 文件，并由编译器重新组合预览页。

## 11. 验收标准

### 11.1 第一阶段

1. 每个新建快照都有可查询的体积诊断记录。
2. 对具有大量重复组件的真实页面，优化后序列化 HTML 相比优化前明显下降；具体目标以首批真实样本的中位数和 P90 数据确定。
3. 去重前后安全清理结果、节点数、稳定源码 ID、文本、表单状态和选区映射一致。
4. 工作区编译后可正常预览、选择元素、连续编辑、撤销重做和导出截图。
5. 至少覆盖普通流、Flex、Grid、定位容器和滚动区域五类布局的浏览器回归验证。

### 11.2 第二阶段

1. 只有无损优化后仍超限时，才展示范围选择。
2. 用户选择任一范围前，系统明确展示其保留与丢失范围；取消后不创建不完整副本。
3. 重新采集后的工作区和 Agent 只可操作实际捕获内容，不能声称修改未捕获区域。
4. 所有超限失败均返回真实的体积构成和下一步选择。

### 11.3 模块化工作区

1. 每个可编辑 `sourceId` 都可解析到唯一的模块归属及其源码范围。
2. Agent 针对局部选区的首轮读取以模块摘要和局部 HTML/CSS 为主，不默认读取整页源码。
3. 模块索引与当前 Revision 一致；撤销、重做和导入后不会指向旧版本行号或节点。
4. 模块化索引不改变预览页 DOM、样式和布局；至少覆盖普通流、Flex、Grid、定位容器和滚动区域。
5. 跨模块需求能够显式识别涉及模块并扩展读取范围，不因模块边界阻断合理编辑。

## 12. 实施顺序与决策点

### M1：诊断与无损去重

实现采集指标、稳定样式指纹、基础样式去重、服务端工作区兼容和回归测试。上线后收集真实页面样本，确认节省比例、剩余大包构成和浏览器渲染一致性。

### M2：阈值与超限引导

根据 M1 数据配置提示/告警/硬限制，补齐超限提示和“当前可见范围”重新采集路径。

### M3：选择区域及结构上下文

在用户明确选择区域后，引入通用的结构上下文捕获、边界说明和真实浏览器验证。此阶段需要单独评审上下文识别规则，禁止采用固定 DOM 层数或业务页面特例。

### M4：逻辑模块化工作区

在稳定的 `outline.json`、`source-map.json` 与 Revision 机制上，生成 `module-map.json` 和模块摘要。
先把它接入 Agent 的检索顺序与日志观测，验证复杂页面中局部任务的读取范围、调用次数和完成质量；
只有指标表明模块边界足够稳定时，再评审物理模块拆分。
