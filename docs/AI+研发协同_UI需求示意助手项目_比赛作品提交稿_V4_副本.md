## 项目简介

**项目名称：** AI+研发协同：UI需求示意助手

**项目方向：** AI+研发协同 / 工程效能提升

**项目简述：**

产品经理最难表达的往往不是“要做什么”，而是“做出来以后应该长什么样”。传统方式下，产品经理仅依靠文字描述 UI 改动，研发需要反复确认位置、样式和交互状态，一个简单调整可能产生多轮沟通和返工。

本项目面向缺少设计资源、需要快速推动需求落地的产品经理，提供一款运行于 Chrome Side Panel 的 AI UI 需求示意助手。它以真实业务页面为上下文，让产品经理直接描述希望看到的变化；系统在隔离的示意环境中完成页面调整，并通过安全校验和版本机制保证结果可控、可回退。

用户无需从空白画布重新搭建原型，只需在真实页面副本中选中目标区域，用自然语言描述修改要求（如“在订单状态右侧增加订单来源和负责人，宽度保持一致”），系统即可生成贴近原页面结构和视觉风格的 UI 示意。

**核心价值数据**

1. 单个 UI 需求示意从约 **4 小时**缩短到约 **10 分钟**，效率提升约 **24 倍**。
2. 时间投入约减少 **95.8%**。产品经理可以直接在真实页面上下文中表达需求，研发获得可视化的共同参照。

## 项目背景、目的与意义

### 一、业务背景

在真实工作中，产品经理需要说明页面改动，但需求往往只能表述为“在这里增加一个筛选项”“样式与相邻组件保持一致”“展开后显示若干选项”等文字要求。

研发拿到文字后，通常还需要进一步确认位置、宽度、组件类型、默认状态和边界条件。产品经理可能需要补充截图、绘制草图或重新搭建原型。一个看似简单的 UI 调整，可能因此产生多轮沟通和返工。

UI 需求示意助手把这段沟通前移：产品经理直接在熟悉的业务页面上表达，AI 负责把自然语言变成页面中的具体变化。研发看到的是带有真实上下文的结果，而不是脱离页面的抽象描述。

### 二、核心痛点

1. **表达难**：页面改动意图难以仅通过文字准确传达，“在这里”“和旁边一样”等描述容易产生歧义。
2. **成本高**：从空白原型开始搭建，成本高、速度慢，也容易偏离真实页面的结构和风格。
3. **沟通反复**：位置、样式、状态和交互细节缺少共同参照，产品与研发之间容易反复确认。
4. **验证难**：面对复杂页面，传统方式很难快速验证“改完以后是否协调”。
5. **安全风险**：AI 如果直接拥有页面脚本、网络和任意文件权限，体验提升的同时也会带来安全风险。

### 三、项目目标

项目希望把“重新制作原型”简化为“在真实页面副本上描述修改”：

1. 打开页面，进入不影响原系统的静态副本；
2. 点选目标区域，用自然语言描述修改要求；
3. AI 复用原页面的组件和样式，生成可视化结果；
4. 继续对话，直到位置、内容和状态符合预期；
5. 导出截图，为研发提供明确的视觉参考。

项目同时坚持三条边界：**原业务页面只读、模型能力受控、静态副本不具备真实业务操作能力。**

### 四、为什么是现在

本项目的技术条件和业务需求在当前时间点形成了最佳交汇：

- **大模型代码能力已达可用水平**：DeepSeek 等模型在 HTML/CSS 代码理解和生成方面的能力已经能够支撑真实页面级别的修改任务，不再停留在概念演示阶段。
- **企业 AI 辅助研发需求迫切**：在降本增效的大背景下，各团队都在探索 AI 如何真正嵌入研发流程、产生可量化收益，而非停留在聊天工具层面。
- **安全可控的示意环境已经具备落地条件**：项目验证了“先冻结页面、再修改副本”的方案能够在不影响原业务页面的前提下支撑快速试错，为内部推广提供了可控边界。
- **浏览器插件形态轻量易推广**：Chrome Side Panel 形态无需独立安装客户端，产品经理可以在日常工作中直接使用，推广成本低。

## 价值分析

### 一、缩短从需求描述到示意结果的路径

产品经理不需要先掌握复杂的设计工具，也不需要从空白画布开始搭建。面对真实页面，选中目标区域并描述修改要求即可获得可评审的 UI 示意。

### 二、建立产品与研发的共同视觉参照

需求截图同时保留原页面上下文、修改位置、组件样式和展示状态。产品和研发可以围绕同一结果讨论实现方式，减少因信息缺失产生的猜测和重复确认。

### 三、在可控边界内使用 AI

AI 只编辑隔离副本中的 HTML/CSS，不能调用真实接口、提交业务数据或执行原页面脚本；系统通过受控工具和确定性校验约束模型行为。这使得 AI 辅助可以在企业安全规范内落地，而不是停留在“个人玩具”层面。

### 四、当前可验证成果

1. **固定场景回归：20/20 通过。** 覆盖添加、修改、删除、多轮指代、状态展示和安全阻断。
2. **工程稳定性回归：12/12 通过。** 覆盖选区切换、撤销重做、事务回滚、截图和标签页隔离。
3. **复杂能力验证：挑战用例与真实页面均已跑通。** 覆盖复杂布局、组件复用、结构移动和多轮修改。
4. **自动化质量：28 个测试文件、136 项测试通过。** 覆盖快照、Workspace、Agent、策略、日志、扩展和评测内核。

上述人工回归和自动化测试结果属于工程稳定性证据，用于证明 Demo 的关键链路具备可重复验证和持续迭代基础，不作为直接业务收益指标。

### 五、真实场景初步收益

在 2026 年 8 月 6 日的一次真实需求场景验证中，对同一页面 UI 调整任务进行了人工方式与工具辅助方式的耗时对比：

- **传统交互设计方式：** 完成耗时约 0.5 个工作日，即约 4 小时；需要依次完成页面结构理解、交互方案设计和示意产出。
- **UI 需求示意助手：** 完成耗时约 10 分钟；产品经理在真实页面副本中完成选区、自然语言描述和 UI 示意生成。

按 8 小时工作日折算，该案例的示意制作耗时从约 4 小时降低到约 10 分钟，**时间投入约减少 95.8%，效率约提升 24 倍**。

**数据说明：** 该结果目前属于单个真实案例的初步观察，不能直接等同于所有需求场景的普遍收益；后续将通过更多样本验证不同复杂度下的稳定收益。

### 六、推广收益目标测算（试点预期）

## 项目方案

### 一、总体设计

项目采用“浏览器捕获层—静态源码工作区—通用源码 Agent—受控文件工具—预览与版本层”的闭环架构。

原业务页面始终只读。插件捕获浏览器当前已经渲染的页面状态，移除活动能力，并生成可维护的静态工作区：

- **index.html：** 保存静态页面结构。
- **snapshot.css：** 保存页面可见样式。
- **outline.json：** 保存页面语义结构摘要。
- **source-map.json：** 保存页面元素与源码位置的映射关系。

用户在副本中选区后，Agent 不接收整页 DOM，而是通过页面结构摘要、搜索和局部读取按需获取上下文，再修改 HTML/CSS。每次修改必须通过格式、安全和空间范围校验，成功后才形成新的 Revision。

**核心操作流程**

1. **进入副本**：产品经理在普通 HTTP/HTTPS 页面打开插件，确认进入副本编辑。
2. **冻结页面**：插件捕获当前页面、表单值、勾选状态、已打开弹窗和可见样式。
3. **安全裁剪**：移除脚本、事件、接口、表单提交、远程导航和外链资源。
4. **生成工作区**：Agent Service 把快照编译为独立 HTML/CSS 源码和语义索引。
5. **选择区域**：用户在副本中选择要修改的元素或局部容器。
6. **描述需求**：用户用自然语言说明新增、修改、移动、删除或展示状态。
7. **源码编辑**：通用 Agent 搜索和读取相关源码，调用受控工具完成修改。
8. **安全校验**：服务检查 HTML/CSS、危险内容、文件范围和新增模块位置。
9. **形成版本**：修改成功后生成 Revision，并刷新副本预览。
10. **继续调整**：用户可继续对话、重新选区、撤销、重做或恢复初始版本。
11. **交付结果**：用户导出当前可视区域截图，作为需求评审和研发沟通材料。

### 二、产品方案

**1. 当前功能范围**

- 真实页面静态快照；
- 当前表单值、勾选状态和已打开弹窗冻结；
- 副本页面元素选择与空间锚点；
- 文案和可见样式修改；
- 按钮、文本、链接、输入框、下拉框、单选、多选、标签、提示条、表格和表单模块等常见内容新增；
- 元素结构移动和克隆；
- 静态弹层和展开状态展示；
- 多轮对话；
- 撤销、重做和恢复初始版本；
- 当前可视区域截图；
- Agent 实时进度和日志查看；
- 复杂布局下的组件复用、位置调整和展示状态示意。

**2. 暂不包含**

- 真实接口调用和业务提交；
- 跨页面业务流程；
- 执行原页面 JavaScript；
- React/Vue 源项目还原；
- 生产代码生成和自动回写业务代码仓库；
- 多人在线协作；
- 完整还原 Canvas、视频、动画、跨域字体和所有复杂伪元素；
- 未经脱敏的敏感业务页面处理。

**3. 与现有方案的差异化对比**

**需求表达起点。** 传统原型工具通常从空白画布开始，需要重新搭建页面；通用 AI 对话工具主要依赖纯文字描述，缺少真实页面上下文；本项目直接以真实业务页面为起点，在隔离副本中完成修改。

**与原页面的一致性。** 传统原型工具需要人工还原结构和样式，容易与真实页面脱节；通用 AI 生成结果与业务页面通常存在明显差异；本项目基于原页面快照生成，能够更好地保留原有结构和视觉风格。

**使用门槛。** 传统原型工具要求用户掌握专业设计能力；通用 AI 对话工具虽然使用简单，但难以准确表达页面位置；本项目通过“自然语言 + 页面点选”完成需求表达，产品经理可以快速上手。

**上下文完整性。** 传统原型和通用 AI 工具往往脱离真实业务页面；本项目保留原页面的视觉、结构和局部业务上下文，使产品与研发能够围绕同一个结果沟通。

**安全可控性。** 通用 AI 工具通常缺少针对企业页面编辑的能力边界；本项目通过隔离副本、受控工具和多层校验限制 Agent 行为，并确保不影响原业务页面。

**交付物形态。** 传统原型工具输出设计源文件，研发仍需二次理解；通用 AI 工具多输出文字或概念图；本项目直接生成可查看、可继续修改、可导出截图的页面示意。

**适用场景。** 传统原型工具适合完整产品原型设计，通用 AI 工具适合问答和创意生成；本项目聚焦 UI 需求快速示意与产品、设计、研发、测试之间的协同沟通。

### 三、技术架构

本项目的技术核心不是“调用一个 Agent 修改页面”，而是建立了一条面向 UI 需求示意的受控生成链路：

完整处理链路包括：

1. 捕获运行态页面状态并进行安全裁剪；
2. 生成可维护的静态源码与语义索引；
3. 构建渐进式上下文；
4. 由受控源码 Agent 理解需求并选择工具；
5. 执行原子化 HTML/CSS 修改；
6. 完成空间范围、安全性和可预览性校验；
7. 通过 Revision 事务提交结果并形成交付物。

其中，模型只负责理解需求和选择下一步工具；页面快照、源码结构、操作权限、校验规则、版本提交和回滚均由系统确定性控制。这样既保留了大模型处理复杂自然语言的能力，又避免把页面修改结果完全交给不可预测的自由生成。

**1. 六项关键技术能力**

1. **运行态页面编译。** 针对浏览器 DOM 不适合长期被 Coding Agent 修改的问题，将已渲染页面转换为可维护的 HTML、CSS、Outline 和 Source Map，并冻结表单值、弹窗和可见样式。
2. **渐进式上下文。** 针对整页 DOM 和样式导致 Token 浪费、定位不准的问题，先向 Agent 提供页面结构摘要和选区，再按需搜索元素、读取局部源码和完整样式规则。
3. **受控源码协议。** 针对自由修改代码容易越界或破坏页面的问题，将读取、替换、移动、克隆、Patch、校验和提交封装为能力边界明确的工具。
4. **语义空间约束。** 针对“右侧、下方、附近”等位置描述容易执行错误的问题，以选区和最近语义容器作为默认锚点，对新增模块执行空间归属校验。
5. **Revision 事务模型。** 针对修改失败后出现页面半成品或上下文分支污染的问题，所有修改先在 Working Copy 中执行，校验通过后才提交 Revision；失败自动回滚，撤销版本时同步截断后续对话上下文。
6. **可观测评测闭环。** 针对 Agent 执行过程难以解释、复杂场景难以持续优化的问题，记录模型调用、工具调用、耗时、源码操作和校验结果，并使用固定回归集、挑战集和真实案例持续评估。

这六项能力共同构成了“自然语言需求—页面示意”的工程闭环，也是本项目区别于通用网页聊天机器人或简单 DOM 修改脚本的关键。

**2. 为什么采用通用源码 Agent**

静态副本本质上是一组 HTML/CSS 文件，任务与通用 Coding Agent 修改代码高度相似。项目没有重复建设通用的上下文管理、Loop、记忆和工具调度能力，而是通过 Adapter 接入 Cline SDK，并将 UI 需求理解、页面语义、源码工具和安全策略接入现有 Agent Loop。

这种复用不是简单替换模型接口：Adapter 负责注入当前工作区、选区、对话分支和文件工具，同时监听每一步源码操作和校验结果；项目自研层负责决定 Agent 能读什么、改什么、何时回滚以及什么条件下允许提交。模型调用层保持可替换，当前接入 DeepSeek；Legacy Adapter 作为回退路径。

**3. 通用层与业务层分工**

- **通用 Agent Runtime：** 负责模型调用、上下文管理、循环执行、工具调度、错误处理和收敛控制，优先复用 Cline SDK、Vercel AI SDK 等成熟能力。
- **UI 源码业务层：** 负责页面语义、选区锚点、修改目标以及样式和结构约束，由项目结合业务场景建设。
- **受控工具层：** 提供搜索、局部读取、样式读取、移动、克隆、Patch 和校验等能力，由项目建设并严格限制操作范围。
- **工作区层：** 负责源码文件、Revision、撤销重做和静态预览，由项目建设。
- **安全层：** 负责页面裁剪、路径隔离、CSP、敏感信息和危险内容校验，由项目建设。

**4. 受控源码工具**

Agent 可使用的主要能力包括：

- 页面 Outline 和元素检索；
- 按 sourceId 检查元素；
- 局部读取 HTML/CSS；
- 一次读取完整样式规则；
- 移动已有结构；
- 克隆已有结构并保留样式；
- 精确文本替换；
- 受控 Patch；
- HTML/CSS 和安全校验；
- 新增元素空间范围校验；
- 提交、完成或请求用户澄清。

Agent 不能访问 Shell、任意网络、浏览器控制能力、其他目录或其他用户工作区。

**5. 分层技术架构**

1. **插件交互层**：WXT、React、Chrome MV3 Side Panel。
2. **快照捕获层**：读取运行态页面、表单状态、弹窗和计算样式。
3. **快照编译层**：安全裁剪、HTML 格式化、CSS 去重、Outline 和 Source Map。
4. **Agent Service**：Hono HTTP 服务、DeepSeek 模型调用、Cline Adapter。
5. **源码编辑层**：通用 Agent 和受控源码工具。
6. **工作区层**：文件、Revision、撤销重做与静态预览。
7. **安全层**：路径隔离、危险内容校验、CSP 和体积限制。
8. **可观测与评测层**：JSONL 日志、实时进度、Vitest 和挑战场景评测。

**6. 安全设计**

安全是企业级 AI 工具能否推广的前提。本项目从授权、页面、工作区、预览、版本和可追溯六个维度构建了完整的安全防线。

**（1）最小授权：** 插件采用 activeTab 临时授权，不申请 all_urls 长期权限，仅处理用户主动打开并授权的普通 HTTP/HTTPS 页面。

**（2）页面主动去能力：** 捕获阶段移除 script、iframe、on* 事件、表单 action、外链资源、React/Vue 运行时标记、Cookie、LocalStorage 等。

**（3）工作区隔离：** Agent 只能访问当前 Workspace 中允许编辑的源码文件，所有路径经过 realpath 校验，禁止通过上级目录逃逸或符号链接攻击。

**（4）预览隔离：** 静态副本通过 CSP 禁止脚本、接口、表单提交和页面导航，确保示意页不能转化为真实业务操作工具。

**（5）版本与恢复：** 每次成功修改形成一个 Revision。校验失败不提交；撤销后对应无效分支的对话上下文也会被截断。

**（6）可追溯：** 日志记录用户指令、Agent 操作摘要、工具结果、校验状态、Revision、模型/工具调用次数和耗时，并对敏感字段脱敏。

**当前安全边界：** Demo 主要在公司内部开发和验证环境运行，正式试点前仍需补充统一鉴权、用户工作区隔离、持久化存储、自动过期清理、限流和日志访问权限。

## 发展规划

本项目的长期目标不是增加更多孤立的 UI 操作，而是逐步改变企业内部“需求如何被表达、评审和实现”的方式：

**发展愿景：从一个帮助产品经理快速生成页面改动示意的工具，发展为连接产品、设计、研发和测试的 AI UI 需求协同平台。**

### 一、第一阶段：内部推广（0～3 个月）

**目标**：验证并复制需求可视化价值，形成可复制的推广模式。

**关键动作**：

- 选择 1～2 个低风险、已脱敏的内部系统作为试点；
- 面向产品经理和交互设计同学开展小范围试用，覆盖新增字段、筛选项、按钮、表格、弹窗、状态和布局调整等高频需求；
- 建立“需求描述—页面示意—研发反馈—结果修正”的闭环记录；
- 沉淀适合内部业务的使用方法、示例库和场景模板。

**阶段目标（拟）**：

- 覆盖不少于 20 名产品经理；
- 收集不少于 100 个真实 UI 需求样本；
- 平均示意制作耗时降低 70% 以上；
- 产品与研发 UI 细节确认轮次减少 40% 以上；
- Agent 首次完成率达到 70% 以上。

### 二、第二阶段：流程接入（3～6 个月）

**目标**：将 UI 示意从个人工具升级为需求评审流程中的标准环节。

**关键动作**：

- 接入公司现有需求平台，使指令、选区、示意截图、Revision 和评审意见直接关联到需求条目；
- 产品经理在需求上下文中创建和调整示意，研发和设计人员在同一条需求下查看修改前后结果；
- 沉淀结构化 UI 变更说明、页面状态清单和评审结论；
- 保留需求从提出、修改到确认的完整版本轨迹。

**阶段目标（拟）**：

- 接入至少 1 个核心需求平台；
- 试点团队的 UI 需求评审中，示意截图覆盖率达到 80%；
- 因 UI 理解偏差导致的返工率降低 30% 以上。

### 三、第三阶段：能力升级（6～12 个月）

**目标**：从局部示意走向页面体验重构，形成企业级 AI UI 协同能力。

**关键动作**：

- 沉淀企业组件、视觉规范和业务页面模式，使 AI 能够识别并遵循公司 UI 规范；
- 能力范围从单个区域扩展到页面级信息架构、模块重排、多状态方案、不同角色视图；
- 支持多个页面方案对比，帮助产品经理在需求早期识别遗漏状态和体验问题；
- 最终形成覆盖“需求描述—方案生成—评审确认—研发理解—测试验收”的全链路协同。

**阶段目标（拟）**：

- 沉淀企业级 UI 组件库适配规则，覆盖核心业务系统；
- 支持页面级方案生成与对比；
- 覆盖产品、设计、研发、测试四类角色的协同场景。

## 核心创新与竞争优势

本项目的竞争优势不在于采用了某一种页面编辑技术，而在于改变了 UI 需求从提出到达成共识的方式。与传统“文字描述 + 重新画原型 + 多轮确认”的方式相比，项目形成了以下差异化价值。

### 一、真实页面驱动的低门槛需求表达

传统原型工具通常要求用户从空白画布开始搭建，容易出现原型与真实页面结构、视觉风格和业务上下文脱节的问题。本项目直接以用户正在使用的真实业务页面作为需求表达起点，产品经理无需重新搭建页面框架，只需选定目标区域并描述修改要求。

系统生成的示意同时保留原页面的上下文和视觉语言，使“增加一个字段”或“调整一个按钮”不再需要先转化为设计工具中的抽象图形，降低产品经理表达 UI 需求的门槛，也提高研发理解需求时的上下文完整性。

### 二、面向多角色协同的共同视觉结果

传统需求沟通中，产品经理的文字、设计稿、研发实现和测试用例往往分别表达同一项 UI 变化，角色之间容易出现理解偏差。本项目将抽象文字转化为产品、设计、研发和测试都能理解的可视化结果，并保留用户指令、修改前后状态和版本关系。

不同角色可以围绕同一结果分别确认业务意图、视觉方案、实现方式和验收范围；当需求发生变化时，也可以继续对话、撤销或重做，而不是重新开始制作原型。项目因此不仅提高单次示意效率，也改善了需求在团队中的协作质量。

### 三、可控、可推广、可持续演进的企业能力

项目在不修改生产页面、不执行真实业务操作的前提下提供 AI 辅助示意能力，既保留自然语言交互的灵活性，也通过页面隔离、权限限制和结果校验控制使用风险，因此适合在内部真实场景中逐步推广。

更重要的是，项目的产品边界具有持续扩展能力：一期可以解决单个页面改动，后续可以接入需求平台、企业组件规范、设计评审和研发任务，再进一步支持页面级体验重构。它不是一次性的原型生成工具，而是可以随着企业页面资产和协作流程沉淀不断增强的 AI UI 需求协同入口。

综合来看，项目的核心创新可以概括为：

**核心创新总结：让产品经理在真实页面中表达需求，让 AI 将抽象描述转化为可评审结果，让产品、设计、研发和测试围绕同一个结果形成共识。**

## 风险与应对

1. **复杂页面还原风险。** 部分复杂页面可能出现快照还原不完整或样式错位。项目采用渐进式增强策略，优先覆盖高频场景并持续优化快照编译能力，同时保留人工补充编辑的兜底方式。目前固定场景和复杂案例已经验证，复杂页面仍在持续优化。
2. **Agent 结果偏差风险。** Agent 生成结果可能不符合预期，需要多轮调整。项目通过渐进式上下文、受控工具、校验机制、撤销重做和挑战集评测持续提升效果。目前已建立多轮挑战集，首次完成率将在内部试点中持续统计。
3. **敏感数据风险。** 页面快照可能包含敏感业务数据。当前仅处理已脱敏页面，并移除 Cookie、LocalStorage 等存储信息，对 API Key 等敏感字段进行日志脱敏；正式试点前还将补充统一鉴权和用户工作区隔离。
4. **Agent 越权风险。** Agent 可能尝试越权操作或生成危险内容。项目通过受控源码工具、路径隔离、危险内容校验、CSP 预览隔离和 Revision 事务机制形成多层防护，目前相关校验已经实现。
5. **用户推广风险。** 产品经理可能因使用习惯而缺少使用意愿。项目将从高频痛点场景切入，通过浏览器插件降低使用门槛，并以真实效率数据验证价值，推广效果将在内部试点中进一步评估。
6. **产品定位风险。** 项目可能被误解为替代设计师或产品经理。项目明确定位于辅助需求表达和沟通，输出的是需求示意而非正式设计稿，不替代专业设计和产品决策。
7. **模型成本风险。** 模型调用成本可能随任务复杂度增加。项目通过渐进式上下文减少 Token 消耗，记录单任务成本，设置合理调用边界，并保持模型可替换。目前已具备 Token 统计和模型替换能力，实际成本数据待试点验证。
8. **页面差异风险。** 不同业务页面之间差异较大，效果可能难以标准化。项目通过分层归因、固定回归集、挑战集和真实案例持续评测，并逐步沉淀场景模板和最佳实践。目前评测体系已经建立。
