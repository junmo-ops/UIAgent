## 一、先理解整体链路

### 1.1 部署流程图

```text
进入云原生应用管理平台“创建应用”
        │
        ▼
填写应用和服务单元基本信息
        │
        ▼
开启“创建流水线”，绑定代码仓库和分支
        │
        ▼
编辑服务单元配置：端口、实例、环境变量等
        │
        ▼
流水线自动执行编译、制品发布、校验和通用部署
        │
        ▼
自动生成镜像并部署服务
        │
        ▼
服务实例启动并通过平台检查
        │
        ▼
使用域名和接口进行验证
```

### 1.2 每个环节为什么存在

**创建应用**：在云原生应用管理平台中建立应用和服务单元，是整个部署流程的入口。

**服务单元**：描述实际运行的 Node.js 服务，包括工作负载类型、架构、端口、实例规格和环境变量等。

**代码仓库**：保存服务源代码、依赖声明、编译配置和 Dockerfile，是自动创建的流水线的输入。

**流水线**：提供统一的构建环境，负责安装依赖和编译代码，解决“谁来构建、用什么 Node 版本构建”的问题。

**Dockerfile**：描述服务运行时使用什么基础镜像、文件放在哪里、开放什么端口以及如何启动。

**镜像仓库**：保存已经构建好的镜像版本。云平台部署的是镜像，不是直接运行代码仓库中的文件。

**通用部署**：流水线的最后一步，自动将生成的镜像部署到云原生应用管理平台，不需要再手工发布一次。

**健康检查**：判断服务进程是否已经能够正常接收请求，不等同于业务接口测试。

### 1.3 三个环境要保持一致

部署时至少存在三个运行环境：本地开发环境、流水线编译环境、Docker 镜像运行环境。云原生应用管理平台负责运行最终镜像。

需要重点保持一致的内容包括：Node.js 主版本、pnpm 版本、依赖版本、CPU 架构、服务端口和启动命令。否则可能出现“本地能跑、流水线不能编译”或“镜像构建成功、服务启动失败”。

## 二、按照平台配置项逐步部署

下面的配置项名称可能因平台版本不同略有差异。每项都标记了建议：

- **必配**：不配置通常无法构建或启动；
- **按需**：根据服务实际情况配置；
- **不建议**：Demo 或普通 HTTP 服务通常不需要配置。

| 发布容器制品库 | 默认步骤 | 将编译结果制作成容器镜像并发布到镜像仓库。 |

项目应在 `package.json` 中声明包管理器版本：

```json
{
  "packageManager": "pnpm@【行内可用的 pnpm 版本】"
}
```

依赖版本必须先在内部 npm 仓库确认：

```bash
npm view <package-name> versions \
  --registry=【内部 npm 仓库地址】 --json
```

修改 `package.json` 后，必须同步更新 `pnpm-lock.yaml`，否则冻结安装会失败。

#### 架构与 Dockerfile 的匹配注意事项

平台页面中的“国产化（C86）”、Linux 和 Kylin 构建环境共同决定了服务的运行约束。Dockerfile 中的基础镜像必须与该架构匹配。

这一项不是自动化编译页面中的独立字段，而是代码仓库中 Dockerfile 的配置约束：

Dockerfile 示例：

```dockerfile
FROM 【国产化 Node.js 基础镜像地址】

COPY ./dist /opt/deployments/dist
COPY ./package.json /opt/deployments/package.json
COPY ./node_modules /opt/deployments/node_modules

WORKDIR /opt/deployments

EXPOSE 5000

CMD ["node", "dist/index.js"]
```

平台通常要求应用文件放在 `/opt/deployments/` 下。具体目录权限以基础镜像说明为准。

### 2.9 部署后验证

```bash
curl -i https://【服务访问域名】/health
```

确认返回 200 后，再验证需要认证的接口：

```bash
curl -i \
  -H "Authorization: Bearer 【访问令牌】" \
  https://【服务访问域名】/v1/health
```

最后验证核心业务接口，并同时查看服务日志，确认请求已经到达当前实例。

流水线的“通用部署”步骤完成后，服务就已经部署完成，不需要再在云原生应用管理平台手动执行一次发布。

## 三、部署过程中常见的坑

### 3.1 Node.js 和 pnpm 版本不匹配

**现象**：pnpm 启动时报 Node.js 不支持某个 `node:` 模块导出，或 Corepack 无法获取 pnpm。

**原因**：流水线 Node 版本较低，但使用了只支持更高 Node 版本的 pnpm。

**避免方式**：先确认平台可用的 Node 和 pnpm 版本，固定 `packageManager`，不要在流水线中获取 latest。

### 3.2 内部 npm 仓库没有公网版本

**现象**：`ERR_PNPM_FETCH_404` 或 `ERR_PNPM_NO_MATCHING_VERSION`。

**原因**：依赖版本在公网存在，但内部 npm 仓库尚未同步，或者 lockfile 解析到了更高版本。

**避免方式**：依赖升级前先用内部仓库查询版本；必要时使用精确版本；重新生成并检查 lockfile。

### 3.3 lockfile 没有同步

**现象**：`ERR_PNPM_OUTDATED_LOCKFILE`、`ERR_PNPM_LOCKFILE_MISSING_DEPENDENCY`。

**原因**：只修改了 `package.json`，没有重新生成 lockfile，或者合并代码时破坏了 lockfile。

**避免方式**：依赖变更后执行 `pnpm install --lockfile-only`，再用 `pnpm install --frozen-lockfile` 模拟流水线。

### 3.4 国产化配置与基础镜像不匹配

**现象**：流水线提示基础镜像不是对应国产化架构。

**原因**：流水线架构选项和 Dockerfile 的 `FROM` 不属于同一架构。

**避免方式**：先确定平台架构，再选择平台认可的 Node.js 基础镜像；不要直接把公网镜像替换进国产化流水线。

### 3.5 镜像推送失败

**现象**：Kaniko 构建完成后，推送镜像或读取镜像元数据失败。

**原因**：镜像地址、发布单元、标签或仓库认证配置错误。

**避免方式**：检查镜像路径和标签，使用平台 Secret 配置认证，不要把账号密码写入 Dockerfile 或日志。

### 3.6 容器目录没有写权限

**现象**：`EACCES: permission denied`，无法创建目录或安装依赖。

**原因**：容器通常以非 root 用户运行，`/data`、应用目录或系统目录不一定可写。

**避免方式**：使用平台明确允许的目录；运行时尽量不安装依赖；不要在未确认权限的目录中创建文件。

### 3.7 服务启动了但访问失败

按以下顺序检查：

1. 服务是否监听 `0.0.0.0`；
2. 服务端口、Dockerfile 端口和云平台端口是否一致；
3. 健康检查端口和路径是否正确；
4. 路由是否指向当前服务版本；
5. 服务日志中是否有启动异常。

### 3.8 403、500、502、504 的区别

- **403**：认证信息、令牌或访问权限有问题。
- **500**：服务端代码或运行时配置异常。
- **502**：网关无法连接后端，重点检查进程、监听地址和端口。
- **504**：网关等待后端超时，需要结合服务日志判断是模型调用慢、Agent 执行慢还是服务阻塞。
