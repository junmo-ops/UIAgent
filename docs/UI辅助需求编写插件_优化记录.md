# UI 辅助需求编写插件优化记录

## O-001：将高频迭代界面改为服务端直出

**状态：** 待排期  
**优先级：** 中  
**提出日期：** 2026-09-02

### 背景与目标

当前侧边栏对话界面、副本管理和日志页面均随 Chrome 插件打包发布。界面样式、交互细节或文案调整后，需要重新构建、分发并由使用者更新插件，迭代成本较高。

目标是在不牺牲浏览器能力与安全边界的前提下，将高频变化的业务 UI 由服务端直出；后续常规界面更新仅部署服务端，无需重新分发插件。

### 方案边界

保留插件作为稳定的浏览器能力层，负责：

- 选取页面元素、注入内容脚本、截图和打开/切换标签页；
- 保存安装凭证，并代理需要鉴权的服务端请求；
- 校验远程页面来源，并提供受控的消息桥接。

服务端负责直出可高频迭代的业务界面，包括侧边栏对话、执行进度、需求澄清、副本管理和日志查看。

远程 UI 不能直接获得扩展权限或安装令牌。涉及浏览器能力和鉴权请求时，远程 UI 通过定义明确的消息协议请求插件壳，由插件壳完成校验和执行后返回结果。

### 约束与验收标准

- 第一阶段不新增服务端运行时 npm 依赖；前端资源可在行外构建为静态产物并随服务发布。
- 仅调整样式、文案、普通业务交互时，服务端发布后即可生效，不要求用户更新插件。
- 新增 Chrome 权限、修改内容脚本/后台脚本、扩展与服务端桥接协议或安全修复时，仍需发布插件新版本。
- 消息来源、请求类型和参数均需白名单校验；不得向远程页面暴露长期安装令牌。
- 当远程 UI 与插件桥接协议版本不兼容时，应明确提示升级插件，不能静默降级或执行未知请求。

### 建议实施顺序

1. 先迁移侧边栏主界面，验证远程 UI 与插件桥接、鉴权代理和版本兼容机制。
2. 再迁移副本管理与日志页面，统一服务端静态资源发布方式。
3. 稳定后将插件包收敛为浏览器能力层，减少后续插件发版范围。

## O-002：副本导入增加阶段化进度反馈

**状态：** 待排期  
**优先级：** 中  
**提出日期：** 2026-09-02

### 背景与目标

导入副本备份包时，插件目前仅展示整体忙碌状态。备份包较大或包含多个副本时，用户无法判断操作停留在哪个阶段，容易误以为导入失败或重复触发。

目标是在不改变导入结果和数据边界的前提下，明确反馈导入进度与当前处理对象。

### 方案边界

导入流程至少展示以下阶段：

1. 正在读取并校验备份包；
2. 正在解析副本清单，并显示总数量；
3. 正在创建副本，显示“第 N / 总数”；
4. 导入完成，展示成功数量；发生失败时明确失败副本及可重试建议。

进度以实际完成的服务端创建请求为准；不以文件读取开始或按钮点击作为完成依据。导入期间禁用重复提交，但保留页面错误信息，避免用户重复导入相同备份包。

## O-003：插件版本检测与自助下载更新

**状态：** 待排期  
**优先级：** 中  
**提出日期：** 2026-09-02

### 背景与目标

插件目前通过 ZIP 包离线分发。新版本发布后，需要逐一联系使用者并发送安装包，更新触达成本高，也容易出现用户长期停留在旧版本的情况。

目标是在插件启动时检测服务端发布的最新版本；发现版本落后时，在插件内提供明确提示和自助下载入口，由用户完成 Chrome 扩展的手动更新。

### 方案边界

- 服务端发布当前最新版本号、更新说明和 ZIP 下载地址；插件与自身 Manifest 版本进行比较。
- 仅当服务端版本更高时展示非阻塞提示，用户可立即下载或暂不处理；不强制中断当前编辑任务。
- 点击下载后，提供简短操作指引：解压 ZIP、进入 Chrome 扩展管理页、开启开发者模式并重新加载扩展目录。
- 下载包可由 Agent Service 随部署包托管，或由行内制品库/共享下载地址托管；两种方式均不新增服务端运行时 npm 依赖。
- 涉及下载的接口和地址必须使用受控来源；不得将安装令牌附加到公开 URL 或写入下载包。

### 预期收益

使用者可自行获取更新包，发布者只需更新服务端版本信息和下载制品，无需逐一私聊发送 ZIP；同时可以逐步收集旧版本分布情况，为后续强制升级策略提供依据。
