# 从网页源码到可编辑原型：AI 原型生成方案分享

## 一、分享目标

本次分享聚焦一个问题：用户通过浏览器 `Ctrl + S` 保存网页源码并上传后，平台如何将这份源码转化为一个可由 AI 持续修改、可预览、可交付的原型。

本文不讨论浏览器插件本身，也不要求复用完整插件方案。插件只是获取页面的一种入口；核心可复用能力在于源码上传后的静态化编译、页面理解、受控编辑和版本管理。

## 二、先统一产品定位

目标不是“上传一个网页后让 AI 改几处 HTML”，而是将网页沉淀为一份可持续协作的原型资产：

```text
网页源码包
  → 可编辑原型工作区
  → AI 多轮调整
  → 可确认的原型版本
  → 截图、链接或需求文档交付
```

用户在平台中看到的应是一个接近原页面视觉效果、但不再具备真实业务行为的静态原型。用户可以选中页面区域，通过自然语言提出修改，例如：

> 在订单状态右侧增加订单来源和负责人两个筛选项，宽度保持一致。

AI 在原型副本中完成调整，用户继续查看、修改、撤销或确认定稿。

## 三、`Ctrl + S` 解决了什么，未解决什么

`Ctrl + S` 是一个可行的页面输入方式，能够让用户自行将网页保存为 HTML 和资源文件，再上传到平台。它解决的是“页面从哪里来”。

但保存下来的文件通常不能直接作为 AI 编辑对象，常见情况包括：

- HTML 中仍包含脚本、事件属性、跳转链接和表单提交逻辑；
- CSS、字体、图片等资源依赖相对路径或外部地址；
- 页面包含框架运行后的冗余节点和临时属性；
- 同一页面的弹窗、输入值、选中状态等可能无法完整保存；
- 如果直接预览或交给 Agent 修改，可能出现资源丢失、页面失真或安全边界不清的问题。

因此，上传源码包不是原型生成的终点，而是“页面编译”的输入。

## 四、核心方案：构建静态原型工作区

上传后，平台应将源码包编译成一个独立的静态原型工作区，而不是直接在原始压缩包中编辑。

```text
源码包上传
  → 解包与资源归档
  → 静态化编译
  → 页面结构与样式索引
  → 隔离预览
  → AI 受控编辑与版本管理
```

### 1. 解包与资源归档

读取上传的 HTML、CSS、图片、字体等资源，建立工作区文件清单，并统一处理相对路径和资源引用。

目标是让页面在平台预览环境中可稳定打开；资源无法解析时应显式标记，而不是静默丢失。

### 2. 静态化编译：保留页面长相，移除页面行为

原型场景只需要当前页面的结构与视觉效果，不需要真实接口、登录态或业务提交。因此需要在编译阶段移除或禁用：

- JavaScript、内联事件和 `iframe`；
- 表单提交、页面跳转和接口调用；
- Cookie、LocalStorage 等运行态数据；
- 不受控的远程资源与危险内容。

编译后的工作区只承载“页面示意”，不能执行真实业务操作。

### 3. 页面理解：从源码变成可检索的页面模型

仅有 HTML/CSS 文件，AI 很难快速定位“订单状态右侧”“与旁边样式一致”等描述。平台需要补充一层页面索引：

- 页面 Outline：页面区域、容器和主要组件的层级摘要；
- 元素索引：稳定元素标识、文本、标签、属性和所在文件位置；
- 样式索引：元素关联的 CSS 规则与可复用样式；
- 空间信息：元素在预览中的位置、尺寸和相邻关系；
- Source Map：元素与 HTML/CSS 源码片段之间的映射。

这层能力可以理解为给 AI 提供“页面目录”和“定位地图”。

### 4. 隔离预览与工作区版本

每个上传页面生成独立工作区，在隔离域名或隔离路径下预览。用户修改时，系统先在 Working Copy 中执行，校验通过后生成新的 Revision。

工作区需要支持：

- 当前版本预览；
- 撤销、重做和恢复初始版本；
- 版本命名、定稿与原型链接；
- 导出截图或静态原型包；
- 修改记录和操作日志查询。

## 五、AI 如何修改页面：不要直接把整页源码交给模型

AI 编辑页面的难点不在于生成一段 HTML，而在于准确找到目标、遵循页面风格并避免破坏其他内容。

建议采用“渐进式上下文”方式：

```text
用户需求 + 当前选区 + 页面摘要
  → 搜索相关元素
  → 读取局部 HTML/CSS 与关联样式
  → 制定修改计划
  → 执行受控操作
  → 校验并提交版本
```

而不是把整页 DOM、全部 CSS 一次性发送给模型。后者会导致上下文噪声大、Token 消耗高、定位不稳定，也不利于复杂页面的多轮修改。

## 六、受控编辑：让模型理解页面，而不是拥有任意权限

模型负责理解自然语言、判断修改目标和选择操作；平台负责提供受限工具、校验结果和版本控制。

建议为 Agent 提供以下通用能力：

- 检索页面区域和元素；
- 读取局部 HTML/CSS、完整样式规则；
- 修改文案、属性和样式；
- 插入、移动、删除、克隆和重排元素；
- 复用已有组件结构与样式；
- 校验 HTML/CSS、资源引用、空间位置和页面可见性；
- 提交版本、请求用户澄清或放弃本次修改。

Agent 不应直接获得 Shell、任意网络、任意文件路径或生产接口权限。

对于“放在右侧”“样式与相邻组件一致”“页面底部增加一组按钮”等空间语义，优先围绕用户选中元素和其语义容器进行理解；当关键位置、目标或样式条件不充分时，主动向用户澄清后再修改。

## 七、可复用能力边界

### 可作为平台通用底座复用

- 静态原型工作区模型；
- 源码包解包、资源归档和静态化编译；
- 页面 Outline、元素索引、样式索引和 Source Map；
- 渐进式上下文构建；
- 受控源码编辑工具；
- Revision、撤销重做、定稿与导出；
- 隔离预览、安全校验、日志与评测。

### 需要结合平台自身建设

- 上传、解析进度和资源缺失提示体验；
- 图片解析为初始网页的能力；
- 企业组件库、视觉规范和组件推荐；
- 原型与需求文档、特性、评审流程的关联；
- 账号、权限、租户、数据留存等平台能力。

## 八、与“图片生成网页”能力如何组合

图片生成网页与网页源码上传，本质上是两种不同的页面输入方式：

```text
截图 / 设计稿 ─────────────→ 初始 HTML/CSS
                                   ↓
Ctrl + S 网页源码包 ───────→ 静态原型工作区
                                   ↓
                           页面理解与受控编辑
                                   ↓
                         版本化原型与需求交付
```

因此，图片解析能力可以作为“页面输入层”；网页源码上传也可以作为另一种输入层。两者进入统一工作区后，共用页面理解、AI 编辑、预览、版本和交付能力。

图片解析输出建议至少包含可维护的 HTML/CSS、组件边界、元素标识、基础样式和无法可靠识别区域的提示。只有输出一张背景图，无法支持后续稳定编辑。

## 九、推荐落地顺序

### 第一阶段：验证可编辑闭环

支持源码包上传、静态预览、元素点选、文案/样式/基础组件调整、版本回退和截图导出。

目标是验证：用户能否在已有网页基础上，通过自然语言快速获得可评审的页面示意。

### 第二阶段：提升复杂页面编辑质量

建设页面索引、渐进式上下文、组件复用、空间位置理解、需求澄清和日志评测能力。

目标是提升复杂页面、多轮修改和布局调整场景下的成功率与稳定性。

### 第三阶段：接入企业需求流程

支持原型定稿、自动生成结构化变更说明，与需求文档、特性和评审流程建立关联。

目标是让原型从一次性页面效果，成为需求协作与研发交付中的正式资产。

## 十、结论

`Ctrl + S` 是一个成本低、易于落地的页面采集方式，但它只解决了“页面输入”的问题。

原型平台真正的核心竞争力，在于将输入统一转化为“可理解、可编辑、可验证、可追溯”的静态原型工作区，并让 AI 在明确边界内持续完成页面协作。

> 输入页面的方式可以来自网页源码、截图、设计稿，甚至自然语言；原型系统的核心，是将不同输入统一沉淀为可持续协作的页面资产。
