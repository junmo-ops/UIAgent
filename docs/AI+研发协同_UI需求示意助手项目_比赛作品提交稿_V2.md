## 二、项目简介

产品经理最难表达的，往往不是“要做什么”，而是“做出来以后应该长什么样”。

本项目面向缺少设计资源、需要快速推动需求落地的产品经理，提供一款运行于 Chrome Side Panel 的 AI UI 需求示意助手。用户无需从空白画布重新搭建原型，只需在真实页面副本中选中目标区域，并输入“在订单状态右侧增加订单来源和负责人，宽度保持一致”等自然语言要求，系统即可生成贴近原页面结构和视觉风格的 UI 示意。

产品经理可以继续补充“展开下拉框”“将按钮调整为危险样式”“增加一行示例数据”等要求，逐步完善页面示意，并将结果截图交给研发。研发获得的不再是需要反复推断的文字描述，而是包含位置、内容、样式和状态的共同参照物。

项目不修改生产页面，也不生成可直接上线的业务代码，而是将抽象的 UI 需求快速转化为可查看、可讨论、可交付的页面结果。

> **传统方式**：产品经理描述“在这里增加一个筛选项”，研发还需要继续确认位置、宽度、选项和交互状态。
>
> **项目方式**：产品经理在真实页面中选定区域并输入自然语言要求，系统生成页面示意，产品和研发基于同一结果完成确认。
>
> **项目价值**：将 UI 需求从抽象描述转化为可视化、可讨论、可交付的结果。

当前已完成以下关键链路：

- 从真实页面生成可编辑的静态副本；
- 通过自然语言完成新增、修改、移动、删除和状态展示；
- 支持多轮调整、撤销重做和截图交付；
- 具备页面安全隔离、位置校验和全链路日志能力；
- 已通过固定场景、工程回归和真实复杂案例验证。

## 四、项目背景、目的与意义

### 4.1 业务背景

在真实工作中，产品经理需要说明页面改动，但需求往往只能表述为“在这里增加一个筛选项”“样式与相邻组件保持一致”“展开后显示若干选项”等文字要求。

研发拿到文字后，通常还需要进一步确认位置、宽度、组件类型、默认状态和边界条件。产品经理可能需要补充截图、绘制草图或重新搭建原型。一个看似简单的 UI 调整，可能因此产生多轮沟通和返工。

UI 需求示意助手把这段沟通前移：产品经理直接在熟悉的业务页面上表达，AI 负责把自然语言变成页面中的具体变化。研发看到的是带有真实上下文的结果，而不是脱离页面的抽象描述。

### 4.2 核心痛点

1. 页面改动意图难以仅通过文字准确传达。
2. 从空白原型开始搭建，成本高、速度慢，也容易偏离真实页面。
3. 位置、样式、状态和交互细节缺少共同参照，沟通容易反复。
4. 面对复杂页面，传统方式很难快速验证“改完以后是否协调”。
5. AI 如果直接拥有页面脚本、网络和任意文件权限，体验提升的同时也会带来安全风险。

### 4.3 项目目标

项目希望把“重新制作原型”简化为“在真实页面副本上描述修改”：

1. 打开页面，进入不影响原系统的静态副本；
2. 点选目标区域，用自然语言描述修改要求；
3. AI 复用原页面的组件和样式，生成可视化结果；
4. 继续对话，直到位置、内容和状态符合预期；
5. 导出截图，为研发提供明确的视觉参考。

项目同时坚持三条边界：原业务页面只读、模型能力受控、静态副本不具备真实业务操作能力。

## 五、价值分析

### 5.1 缩短从需求描述到示意结果的路径

产品经理不需要先掌握复杂的设计工具，也不需要从空白画布开始搭建。面对真实页面，选中目标区域并描述修改要求即可获得可评审的 UI 示意。

### 5.2 建立产品与研发的共同视觉参照

需求截图同时保留原页面上下文、修改位置、组件样式和展示状态。产品和研发可以围绕同一结果讨论实现方式，减少因信息缺失产生的猜测和重复确认。

### 5.3 在可控边界内使用 AI

AI 只编辑隔离副本中的 HTML/CSS，不能调用真实接口、提交业务数据或执行原页面脚本；系统通过受控工具和确定性校验约束模型行为。

### 5.4 当前可验证成果

| 验证维度 | 当前结果 | 说明 |
| --- | --- | --- |
| 固定场景回归 | 20/20 通过 | 覆盖添加、修改、删除、多轮指代、状态展示和安全阻断 |
| 工程稳定性回归 | 12/12 通过 | 覆盖选区切换、撤销重做、事务回滚、截图和标签页隔离 |
| 复杂能力验证 | 挑战用例与真实页面已跑通 | 验证复杂布局、组件复用、结构移动和多轮修改 |
| 自动化质量 | 28 个测试文件、136 项测试通过 | 覆盖快照、Workspace、Agent、策略、日志、扩展和评测内核 |

### 5.5 真实场景初步收益

在 2026 年 8 月 6 日的一次真实需求场景验证中，对同一页面 UI 调整任务进行了人工方式与工具辅助方式的耗时对比：

| 方式 | 完成耗时 | 结果 |
| --- | ---: | --- |
| 传统交互设计方式 | 约 0.5 个工作日 | 需要完成页面结构理解、交互方案设计和示意产出 |
| UI 需求示意助手 | 约 10 分钟 | 在真实页面副本中完成选区、自然语言描述和 UI 示意生成 |

按 8 小时工作日折算，该案例的示意制作耗时从约 4 小时降低到约 10 分钟，时间投入约减少 95.8%，效率约提升 24 倍。该结果目前属于单个真实案例的初步观察，不能直接等同于所有需求场景的普遍收益；后续将通过更多样本验证不同复杂度下的稳定收益。

### 5.6 后续量化口径

当前收益数据来自单个真实案例，主要用于验证价值方向，尚未形成多样本、生产级统计结论。进入内部试点后，建议继续统计：

- 单个 UI 需求从描述到形成可评审示意的耗时；
- 产品与研发围绕 UI 细节的确认轮次；
- 因需求理解偏差产生的返工次数；
- 研发一次理解率；
- Agent 首次完成率和平均修改轮次；
- 不安全操作的策略阻断率。

建议首轮选择一个低风险、已脱敏的内部系统，连续收集不少于 30 个真实 UI 需求样本，并与原有文字或原型方式做同类任务对照。

## 六、项目方案

### 6.1 总体思路

项目采用“浏览器捕获层—静态源码工作区—通用源码 Agent—受控文件工具—预览与版本层”的闭环架构。

原业务页面始终只读。插件捕获浏览器当前已经渲染的页面状态，移除活动能力，并生成可维护的静态工作区：

```text
index.html
snapshot.css
outline.json
source-map.json
```

用户在副本中选区后，Agent 不接收整页 DOM，而是通过页面结构摘要、搜索和局部读取按需获取上下文，再修改 HTML/CSS。每次修改必须通过格式、安全和空间范围校验，成功后才形成新的 Revision。

![alt text](<ChatGPT Image 2026年8月6日 17_39_49.png>)

### 6.2 核心操作流程

1. **进入副本**：产品经理在普通 HTTP/HTTPS 页面打开插件，确认进入副本编辑。
2. **冻结页面**：插件捕获当前页面、表单值、勾选状态、已打开弹窗和可见样式。
3. **安全裁剪**：移除脚本、事件、接口、表单提交、远程导航和外链资源。
4. **生成工作区**：Agent Service 把快照编译为独立 HTML/CSS 源码和语义索引。
5. **选择区域**：用户在副本中选择要修改的元素或局部容器。
6. **描述需求**：用户用自然语言说明新增、修改、移动、删除或展示状态。
7. **源码编辑**：通用 Agent 搜索和读取相关源码，调用受控工具完成修改。
8. **安全校验**：服务检查 HTML/CSS、危险内容、文件范围和新增模块位置。
9. **形成版本**：修改成功后生成 Revision，并刷新副本预览。
10. **继续调整**：用户可继续对话、重新选区、撤销、重做或恢复初始版本。
11. **交付结果**：用户导出当前可视区域截图，作为需求评审和研发沟通材料。

### 6.3 当前功能范围

- 真实页面静态快照；
- 当前表单值、勾选状态和已打开弹窗冻结；
- 副本页面元素选择与空间锚点；
- 文案和可见样式修改；
- 按钮、文本、链接、输入框、下拉框、单选、多选、标签、提示条、表格和表单模块等常见内容新增；
- 元素结构移动和克隆；
- 静态弹层和展开状态展示；
- 多轮对话；
- 撤销、重做和恢复初始版本；
- 当前可视区域截图；
- Agent 实时进度和日志查看；
- 复杂布局下的组件复用、位置调整和展示状态示意；

### 6.4 暂不包含

- 真实接口调用和业务提交；
- 跨页面业务流程；
- 执行原页面 JavaScript；
- React/Vue 源项目还原；
- 生产代码生成和自动回写业务代码仓库；
- 多人在线协作；
- 完整还原 Canvas、视频、动画、跨域字体和所有复杂伪元素；
- 未经脱敏的敏感业务页面处理。

## 七、技术架构与核心工程能力

本项目的技术核心不是“调用一个 Agent 修改页面”，而是建立了一条面向 UI 需求示意的受控生成链路：

```text
运行态页面
  → 页面状态捕获与安全裁剪
  → 可维护静态源码与语义索引
  → 渐进式上下文构建
  → 受控源码 Agent 推理
  → 原子化 HTML/CSS 修改
  → 空间、安全与可预览性校验
  → Revision 事务提交与结果交付
```

其中，模型只负责理解需求和选择下一步工具；页面快照、源码结构、操作权限、校验规则、版本提交和回滚均由系统确定性控制。这样既保留了大模型处理复杂自然语言的能力，又避免把页面修改结果完全交给不可预测的自由生成。

### 7.1 六项关键技术能力

| 能力 | 解决的问题 | 项目实现 |
| --- | --- | --- |
| 运行态页面编译 | 浏览器 DOM 不适合长期被 Coding Agent 修改 | 将已渲染页面转换为可维护的 HTML、CSS、Outline 和 Source Map，冻结表单值、弹窗和可见样式 |
| 渐进式上下文 | 整页 DOM 和样式导致 Token 浪费、定位不准 | 先提供页面结构摘要和选区，再按需搜索元素、读取局部源码和完整样式规则 |
| 受控源码协议 | 自由改代码容易越界或破坏页面 | 将读取、替换、移动、克隆、Patch、校验和提交封装为能力边界明确的工具 |
| 语义空间约束 | “右侧、下方、附近”等需求容易被放错位置 | 以选区和最近语义容器作为默认锚点，对新增模块执行空间归属校验 |
| Revision 事务模型 | 修改失败后页面半成品、上下文分支污染 | 修改在 Working Copy 中执行，校验通过后才提交 Revision；失败自动回滚，撤销版本同步截断后续对话上下文 |
| 可观测评测闭环 | Agent 成功与否无法解释，复杂场景难以持续优化 | 记录模型调用、工具调用、耗时、源码操作和校验结果，并使用固定回归集、挑战集和真实案例持续评估 |

这六项能力共同构成了“自然语言需求 → 页面示意”的工程闭环，也是本项目区别于通用网页聊天机器人或简单 DOM 修改脚本的关键。

### 7.2 为什么采用通用源码 Agent

静态副本本质上是一组 HTML/CSS 文件，任务与通用 Coding Agent 修改代码高度相似。项目没有重复建设通用的上下文管理、Loop、记忆和工具调度能力，而是通过 Adapter 接入 Cline SDK，并将 UI 需求理解、页面语义、源码工具和安全策略接入现有 Agent Loop。

这种复用不是简单替换模型接口：Adapter 负责注入当前工作区、选区、对话分支和文件工具，同时监听每一步源码操作和校验结果；项目自研层负责决定 Agent 能读什么、改什么、何时回滚以及什么条件下允许提交。模型调用层保持可替换，当前接入 DeepSeek。

### 7.3 通用层与业务层分工

| 层级 | 主要职责 | 建设方式 |
| --- | --- | --- |
| 通用 Agent Runtime | 模型调用、上下文、循环、工具调度、错误处理、收敛 | 优先复用 Cline SDK、Vercel AI SDK |
| UI 源码业务层 | 页面语义、选区锚点、修改目标、样式与结构约束 | 项目自研 |
| 受控工具层 | 搜索、局部读取、样式读取、移动、克隆、Patch、校验 | 项目自研并限制能力范围 |
| 工作区层 | 文件、Revision、撤销重做和静态预览 | 项目自研 |
| 安全层 | 页面裁剪、路径隔离、CSP、敏感信息和危险内容校验 | 项目自研 |

### 7.4 受控源码工具

Agent 可使用的主要能力包括：

- 页面 Outline 和元素检索；
- 按 sourceId 检查元素；
- 局部读取 HTML/CSS；
- 一次读取完整样式规则；
- 移动已有结构；
- 克隆已有结构并保留样式；
- 精确文本替换；
- 受控 Patch；
- HTML/CSS 和安全校验；
- 新增元素空间范围校验；
- 提交、完成或请求用户澄清。

Agent 不能访问 Shell、任意网络、浏览器控制能力、其他目录或其他用户工作区。

### 7.5 渐进式上下文

模型不再在每轮接收完整 DOM 和全部样式，而是先获得页面 Outline、当前选区和轻量结构信息；需要时再搜索元素、读取局部源码或完整样式规则。

这种方式能够：

- 降低无关 Token；
- 减少超长 DOM 对模型判断的干扰；
- 让复杂任务围绕实际修改区域逐步展开；
- 把上下文读取过程记录到日志中，方便定位性能问题。

### 7.6 循环与收敛

源码编辑任务允许比简单 DOM 操作更多的工具调用。当前单轮默认最多 45 次迭代，最后 3 轮进入收敛阶段，停止扩展读取，强制 Agent 在“校验并完成”或“向用户澄清”之间做出选择，避免页面已经改完却因未调用完成工具而回滚。

对话记忆与源码 Revision 绑定。用户撤销到旧版本后，被撤销版本对应的对话不会继续发送给下一轮模型，避免旧需求污染新分支。

### 7.7 分层技术架构

1. **插件交互层**：WXT、React、Chrome MV3 Side Panel。
2. **快照捕获层**：读取运行态页面、表单状态、弹窗和计算样式。
3. **快照编译层**：安全裁剪、HTML 格式化、CSS 去重、Outline 和 Source Map。
4. **Agent Service**：Hono HTTP 服务、DeepSeek 模型调用、Cline Adapter。
5. **源码编辑层**：通用 Agent 和受控源码工具。
6. **工作区层**：文件、Revision、撤销重做与静态预览。
7. **安全层**：路径隔离、危险内容校验、CSP 和体积限制。
8. **可观测与评测层**：JSONL 日志、实时进度、Vitest 和挑战场景评测。

### 7.8 技术复用原则

项目遵循“成熟能力复用、关键体验自研”的原则。浏览器插件、模型调用、Agent Loop、协议校验和自动化测试等通用部分采用成熟开源方案；页面状态冻结、静态副本编译、选区语义锚点、受控源码工具、Revision 管理和安全校验等直接决定用户体验与企业使用边界的部分由项目自研。

这种分工既避免重复建设通用基础设施，也把研发投入集中在“真实页面能否被准确表达、复杂需求能否稳定完成、结果能否安全交付”这三个产品关键问题上。

## 八、安全设计

### 8.1 最小授权

插件采用 `activeTab` 临时授权，不申请 `<all_urls>` 长期权限，仅处理用户主动打开并授权的普通 HTTP/HTTPS 页面。

### 8.2 页面主动去能力

捕获阶段会移除：

- `script`、`iframe`、`object`、`embed`；
- `on*` 事件处理器；
- 表单 action；
- HTTP/HTTPS 外链资源和远程导航；
- React/Vue 运行时标记；
- Cookie、Local Storage 和 Session Storage。

### 8.3 工作区隔离

Agent 只能访问当前 Workspace 中允许编辑的源码文件，不能读取仓库其他文件、其他工作区或操作系统目录。

### 8.4 预览隔离

静态副本通过 CSP 禁止脚本、接口、表单提交和页面导航，确保示意页不能转化为真实业务操作工具。

### 8.5 版本与恢复

每次成功修改形成一个 Revision。校验失败不提交；用户可以撤销、重做或恢复初始版本。撤销后，对应无效分支的对话上下文也会被截断。

### 8.6 可追溯

日志记录用户指令、Agent 操作摘要、工具结果、校验状态、Revision、模型调用次数、工具调用次数和耗时，并对 API Key、Authorization、Token、Cookie 和密码等字段脱敏。

当前 Demo 主要在公司内部开发和验证环境运行，正式试点前仍需补充统一鉴权、用户工作区隔离、持久化存储、自动过期清理、限流和日志访问权限。

## 九、关键难点与通用解法

项目在真实页面和复杂需求验证中遇到的难点，主要集中在页面理解、源码编辑、Agent 收敛和安全控制，而不是单个组件的增删改。项目将具体问题抽象为以下通用挑战：

| 核心挑战 | 真实表现 | 通用解法 |
| --- | --- | --- |
| 页面状态还原 | 弹窗、下拉框、表单值、勾选状态、伪元素和计算样式在静态副本中容易丢失或错位 | 建立运行态页面编译链路，冻结结构、样式和可见状态，生成 HTML、CSS、Outline 和 Source Map |
| 页面语义定位 | “在右侧”“放到底部”“放在查询按钮左侧”等描述容易被误解，新内容可能被放到页面顶部或根节点 | 以用户选区和最近语义容器作为默认锚点，结合 `sourceId` 和空间范围校验确定新增模块归属 |
| 组件与样式复用 | 新增 Select 变成纯文本、下拉面板样式不一致、危险按钮样式不完整、提示组件被简化为普通背景 | 优先克隆现有组件结构和样式；对 Select、Dropdown、Popover、Tag、Alert 等复杂组件保留完整静态结构和状态表达 |
| 复杂任务上下文控制 | 整页 DOM 和 CSS 过大导致 Token 消耗高、响应时间长、Agent 读取无关内容 | 采用渐进式上下文，先读取 Outline 和选区，再按需搜索元素、读取局部源码和完整样式规则 |
| Agent 循环与结果收敛 | Agent 可能重复搜索、重复生成补丁，超过多轮后仍未提交，或者页面已修改但没有形成 Revision | 引入完成协议、末轮收敛、重复错误熔断、校验后提交和失败自动回滚 |
| AI 能力与安全边界 | Agent 如果可以执行脚本、调用网络或访问任意文件，可能造成真实业务操作和数据泄露 | 使用静态副本、受控源码工具、路径隔离、CSP、危险内容校验和最小权限模型 |

### 9.1 从运行时页面生成可维护源码

浏览器 DOM 适合展示，却不适合 Coding Agent 反复修改。项目把运行态页面编译为格式化 HTML、去重 CSS、Outline 和 Source Map，使 Agent 可以通过搜索、局部读取和 Patch 完成复杂任务。该过程同时冻结当前表单值、弹窗和可见样式，避免将页面理解简化为一棵缺少状态信息的 DOM 树。

### 9.2 新增模块的位置判断

用户明确描述“页面顶部、页面底部、固定位置或悬浮位置”时，允许使用全局容器；没有明确全局位置时，系统默认围绕当前选中元素或其最近语义祖先定位。该策略解决了“功能完成但位置错误”的典型问题。

新增元素在提交前必须调用 `validate_spatial_scope` 校验。局部需求中新增 `position: fixed` 会被拒绝；无法确定参照容器时，Agent 必须向用户澄清，而不是自行猜测。

### 9.3 组件复用与静态交互表达

复杂组件的难点不只是生成一个标签，而是同时保持其结构、视觉风格和目标状态。例如 Select 的收起态、展开面板、选项样式和锚点位置需要分别处理；按钮、标签和提示条也需要复用原页面的组件语义。项目通过 `clone_element`、样式规则读取和声明式状态属性，避免用一段近似 HTML 代替原组件。

### 9.4 复杂任务的 Agent 收敛

复杂源码任务需要多轮搜索、读取和修改，不能简单限制为少量模型调用。项目在提高迭代预算的同时增加末轮收敛区；检测到相同错误重复出现时，限制无效重试并要求 Agent 更换策略或向用户澄清，避免长时间停留在同一失败路径。

### 9.5 插件生命周期与快照安全清洗

真实验证中还遇到过插件关闭后选区辅助层残留、副本页面切换后编辑会话未及时恢复等生命周期问题，项目通过标签页绑定、连接恢复和辅助 UI 清理机制处理。对于线上页面中的脚本、事件、远程资源和 CSS 外部资源，捕获阶段先执行安全裁剪，再进入源码工作区，确保快照可以预览但不具备真实业务执行能力。

### 9.6 避免按案例逐条特判

项目不增加“订单行”“筛选栏”等业务专用工具，而是通过移动、克隆、样式读取、精确替换、声明式状态和空间校验等通用原子能力覆盖不同页面场景。问题按快照、定位、组件、Agent、校验和预览分层归因，通过回归集、挑战集和真实日志验证通用性。

## 十、发展规划

本项目的长期目标不是增加更多孤立的 UI 操作，而是逐步改变企业内部“需求如何被表达、评审和实现”的方式：

> **从一个帮助产品经理快速画出页面改动的工具，发展为连接产品、设计、研发和测试的 AI UI 需求协同平台。**

### 10.1 内部推广：验证并复制需求可视化价值

第一阶段聚焦内部真实使用，而不是继续堆叠演示功能。选择低风险、已脱敏的内部系统，面向产品经理和交互设计同学开展小范围试用，覆盖新增字段、筛选项、按钮、表格、弹窗、状态和布局调整等高频需求。

推广过程中同步建立“需求描述—页面示意—研发反馈—结果修正”的闭环记录，持续统计示意制作耗时、沟通轮次、返工次数、一次理解率和 Agent 首次完成率，并沉淀适合内部业务的使用方法、示例库和场景模板。阶段目标是验证产品能否稳定降低 UI 需求示意成本，并形成可复制的推广模式。

### 10.2 流程接入：成为需求评审的标准入口

第二阶段将 UI 示意助手从个人工具接入公司现有需求平台，使用户指令、选区、示意截图、Revision 和评审意见直接关联到需求条目。产品经理可以在需求上下文中创建和调整示意，研发和设计人员可以在同一条需求下查看修改前后结果，而不需要在聊天记录、截图和原型文件之间反复切换。

在此基础上，系统进一步沉淀结构化 UI 变更说明、页面状态清单和评审结论，保留需求从提出、修改到确认的版本轨迹。阶段目标是将“需求示意”从个人工作习惯升级为需求评审流程中的标准环节，减少 UI 信息在角色之间传递时的损耗。

### 10.3 能力升级：从局部示意走向页面体验重构

第三阶段在局部编辑能力稳定后，逐步沉淀企业组件、视觉规范和业务页面模式，使 AI 能够识别并遵循公司 UI 规范，优先复用经过验证的组件和交互模式，而不是生成孤立的新样式。

能力范围进一步从单个区域扩展到页面级信息架构、模块重排、多状态方案、不同角色视图和相关页面体验一致性调整，帮助产品经理在需求早期比较多个页面方案、识别遗漏状态并提前发现体验问题。最终形成覆盖“需求描述—方案生成—评审确认—研发理解—测试验收”的企业级 AI UI 协同能力。

## 十二、核心创新与竞争优势

本项目的竞争优势不在于采用了某一种页面编辑技术，而在于改变了 UI 需求从提出到达成共识的方式。与传统“文字描述 + 重新画原型 + 多轮确认”的方式相比，项目形成了以下差异化价值。

### 12.1 真实页面驱动的低门槛需求表达

传统原型工具通常要求用户从空白画布开始搭建，容易出现原型与真实页面结构、视觉风格和业务上下文脱节的问题。本项目直接以用户正在使用的真实业务页面作为需求表达起点，产品经理无需重新搭建页面框架，只需选定目标区域并描述修改要求。

系统生成的示意同时保留原页面的上下文和视觉语言，使“增加一个字段”或“调整一个按钮”不再需要先转化为设计工具中的抽象图形，降低产品经理表达 UI 需求的门槛，也提高研发理解需求时的上下文完整性。

### 12.2 面向多角色协同的共同视觉结果

传统需求沟通中，产品经理的文字、设计稿、研发实现和测试用例往往分别表达同一项 UI 变化，角色之间容易出现理解偏差。本项目将抽象文字转化为产品、设计、研发和测试都能理解的可视化结果，并保留用户指令、修改前后状态和版本关系。

不同角色可以围绕同一结果分别确认业务意图、视觉方案、实现方式和验收范围；当需求发生变化时，也可以继续对话、撤销或重做，而不是重新开始制作原型。项目因此不仅提高单次示意效率，也改善了需求在团队中的协作质量。

### 12.3 可控、可推广、可持续演进的企业能力

项目在不修改生产页面、不执行真实业务操作的前提下提供 AI 辅助示意能力，既保留自然语言交互的灵活性，也通过页面隔离、权限限制和结果校验控制使用风险，因此适合在内部真实场景中逐步推广。

更重要的是，项目的产品边界具有持续扩展能力：一期可以解决单个页面改动，后续可以接入需求平台、企业组件规范、设计评审和研发任务，再进一步支持页面级体验重构。它不是一次性的原型生成工具，而是可以随着企业页面资产和协作流程沉淀不断增强的 AI UI 需求协同入口。

综合来看，项目的核心创新可以概括为：

> **让产品经理在真实页面中表达需求，让 AI 将抽象描述转化为可评审结果，让产品、设计、研发和测试围绕同一个结果形成共识。**

## 十三、当前限制与待补充事项

### 13.1 当前限制

- 快照模式以静态 UI 示意为目标，不保证完整还原复杂动画、Canvas、视频和所有跨域资源。
- 页面数据会发送到内部 Agent Service，当前仅适用于无敏感信息或已经脱敏的测试场景。
- 当前效率收益数据仍为单个真实案例，尚未完成多样本统计。

### 13.2 提交前待补充

- 实际内部试点范围；
- 正式产品截图、前后对比图和技术架构图；
- 更多真实需求样本的效率数据或用户反馈；
- 专利、软著或历史评奖信息（如有）；
- 最终比赛要求的项目名称格式、分行信息和联系人信息。
