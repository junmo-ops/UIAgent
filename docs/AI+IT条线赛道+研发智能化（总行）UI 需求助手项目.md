## 项目简介

**项目名称：** AI+研发协同：UI需求示意助手

**项目方向：** AI+研发协同 / 工程效能提升

**项目简述：**

UI 需求助手是一款面向产品经理的 AI 页面示意工具，运行于 Chrome Side Panel。它以真实业务页面为创作底稿，将自然语言需求直接转化为贴近原页面结构和视觉风格的可视化方案，让产品经理能够在需求提出阶段快速呈现“改完之后是什么样”。

用户无需从空白画布搭建原型，只需进入页面副本、选中目标区域并描述修改要求，例如“在订单状态右侧增加订单来源和负责人，宽度保持一致”。AI 即可完成文案、组件、布局、样式和展示状态等页面调整，并支持连续对话修改、重新选区、撤销、重做和截图交付。

项目提供统一的对话式需求入口。AI 能够结合页面内容和对话上下文理解用户意图，在方案讨论、需求澄清和页面编辑之间自然衔接；对于明确的修改需求，系统形成目标、范围和视觉约束清晰的执行方案，在隔离环境中完成编辑并生成可回退的版本结果。

**核心价值数据**

1. 单个 UI 需求示意从约 **4 小时**缩短到约 **10 分钟**，效率提升约 **24 倍**。
2. 时间投入约减少 **95.8%**。产品经理可以直接在真实页面上下文中表达需求，研发获得可视化的共同参照。

## 项目背景、目的与意义

### 一、业务背景

在真实工作中，产品经理需要说明页面改动，但需求往往只能表述为“在这里增加一个筛选项”“样式与相邻组件保持一致”“展开后显示若干选项”等文字要求。

研发拿到文字后，通常还需要进一步确认位置、宽度、组件类型、默认状态和边界条件。产品经理可能需要补充截图、绘制草图或重新搭建原型。一个看似简单的 UI 调整，可能因此产生多轮沟通和返工。

UI 需求示意助手把这段沟通前移：产品经理直接在熟悉的业务页面上表达，AI 负责把自然语言变成页面中的具体变化。研发看到的是带有真实上下文的结果，而不是脱离页面的抽象描述。

### 二、核心痛点

1. **表达难**：页面改动意图难以仅通过文字准确传达，“在这里”“和旁边一样”等描述容易产生歧义。
2. **成本高**：从空白原型开始搭建，成本高、速度慢，也容易偏离真实页面的结构和风格。
3. **沟通反复**：位置、样式、状态和交互细节缺少共同参照，产品与研发之间容易反复确认。
4. **验证难**：面对复杂页面，传统方式很难快速验证“改完以后是否协调”。
5. **安全风险**：AI 如果直接拥有页面脚本、网络和任意文件权限，体验提升的同时也会带来安全风险。

### 三、项目目标

项目希望把“重新制作原型”简化为“在真实页面副本上描述修改”：

1. 打开页面，进入不影响原系统的静态副本；
2. 点选目标区域，用自然语言描述修改要求；
3. AI 复用原页面的组件和样式，生成可视化结果；
4. 继续对话，直到位置、内容和状态符合预期；
5. 导出截图，为研发提供明确的视觉参考。

项目同时坚持三条边界：**原业务页面只读、模型能力受控、静态副本不具备真实业务操作能力。**

### 四、为什么是现在

本项目的技术条件和业务需求在当前时间点形成了最佳交汇：

- **大模型代码能力已达可用水平**：DeepSeek 等模型在 HTML/CSS 代码理解和生成方面的能力已经能够支撑真实页面级别的修改任务，不再停留在概念演示阶段。
- **企业 AI 辅助研发需求迫切**：在降本增效的大背景下，各团队都在探索 AI 如何真正嵌入研发流程、产生可量化收益，而非停留在聊天工具层面。
- **安全可控的示意环境已经具备落地条件**：项目验证了“先冻结页面、再修改副本”的方案能够在不影响原业务页面的前提下支撑快速试错，为内部推广提供了可控边界。
- **浏览器插件形态轻量易推广**：Chrome Side Panel 形态无需独立安装客户端，产品经理可以在日常工作中直接使用，推广成本低。

## 价值分析

### 一、缩短从需求描述到示意结果的路径

产品经理不需要先掌握复杂的设计工具，也不需要从空白画布开始搭建。面对真实页面，选中目标区域并描述修改要求即可获得可评审的 UI 示意。

### 二、建立产品与研发的共同视觉参照

需求截图同时保留原页面上下文、修改位置、组件样式和展示状态。产品和研发可以围绕同一结果讨论实现方式，减少因信息缺失产生的猜测和重复确认。

### 三、在可控边界内使用 AI

AI 只编辑隔离副本中的 HTML/CSS，不能调用真实接口、提交业务数据或执行原页面脚本；系统通过受控工具和确定性校验约束模型行为。这使得 AI 辅助可以在企业安全规范内落地，而不是停留在“个人玩具”层面。

## 项目方案

### 一、总体设计

项目采用“浏览器捕获层—静态源码工作区—通用源码 Agent—受控文件工具—预览与版本层”的闭环架构。

原业务页面始终只读。插件捕获浏览器当前已经渲染的页面状态，移除活动能力，并生成可维护的静态工作区：

- **index.html：** 保存静态页面结构。
- **snapshot.css：** 保存页面可见样式。
- **outline.json：** 保存页面语义结构摘要。
- **source-map.json：** 保存页面元素与源码位置的映射关系。

用户在副本中选区后，Agent 不接收整页 DOM，而是通过页面结构摘要、搜索和局部读取按需获取上下文，再修改 HTML/CSS。每次修改必须通过格式、安全和空间范围校验，成功后才形成新的 Revision。

图片说明：展示“原业务页面—捕获运行态页面—安全裁剪—静态源码工作区—源码 Agent—校验与预览—交付”的七步闭环，并在底部标注安全边界。

图片规格：16∶9 横版，扁平化企业 SaaS 信息图风格。

**核心操作流程**

1. **进入副本**：产品经理在普通 HTTP/HTTPS 页面打开插件，确认进入副本编辑。
2. **冻结页面**：插件捕获当前页面、表单值、勾选状态、已打开弹窗和可见样式。
3. **安全裁剪**：移除脚本、事件、接口、表单提交、远程导航和外链资源。
4. **生成工作区**：Agent Service 把快照编译为独立 HTML/CSS 源码和语义索引。
5. **选择区域**：用户在副本中选择要修改的元素或局部容器。
6. **描述需求**：用户用自然语言说明新增、修改、移动、删除或展示状态。
7. **理解需求**：AI 结合页面和对话上下文理解用户意图，补齐影响页面结果的关键条件。
8. **确认方案**：Agent 形成目标元素、修改范围和视觉约束清晰的执行方案。
9. **源码编辑**：通用 Agent 搜索和读取相关源码，调用受控工具完成修改。
10. **安全校验**：服务检查 HTML/CSS、危险内容、文件范围、新增模块位置和页面可见性。
11. **形成版本**：修改成功后生成 Revision，并刷新副本预览；任一关键步骤失败则整体回滚。
12. **继续调整**：用户可继续对话、重新选区、撤销、重做或恢复初始版本。
13. **交付结果**：用户导出当前可视区域截图，作为需求评审和研发沟通材料。

### 二、产品方案

**1. 当前功能范围**

- 真实页面静态快照；
- 当前表单值、勾选状态和已打开弹窗冻结；
- 副本页面元素选择与空间锚点；
- 文案和可见样式修改；
- 按钮、文本、链接、输入框、下拉框、单选、多选、标签、提示条、表格和表单模块等常见内容新增；
- 元素结构移动和克隆；
- 静态弹层和展开状态展示；
- 普通问答、页面修改与歧义澄清的统一对话入口；
- 基于页面和对话上下文的语义意图识别，无需用户手动切换模式；
- 多轮对话；
- 撤销、重做和恢复初始版本；
- 历史副本搜索、重命名、移入回收站和恢复；
- 当前可视区域截图；
- Agent 实时进度和日志查看；
- 复杂布局下的组件复用、位置调整和展示状态示意。

**2. 与传统原型工具、通用 AI 工具的差异化对比**

当前 UI 需求表达主要依赖两类工具：一类是 Axure、Figma 等传统原型工具，需要人工搭建页面；另一类是通用 AI 对话或页面生成工具，通常缺少真实业务页面上下文。本项目聚焦真实页面中的 UI 需求示意，核心差异体现在以下五个方面：

**真实页面起步。** 无需从空白画布重新搭建，直接保留业务页面的结构、样式和上下文。

**自然语言编辑。** 通过“页面点选 + 对话描述”表达需求，无需专业原型设计能力。

**可视化结果。** AI 直接生成可查看、可继续调整、可导出截图的页面示意，而非文字建议或概念图。

**安全可控。** 所有修改均在隔离副本中受控执行，不影响原业务页面和真实业务数据。

**持续沉淀。** 页面状态、对话和修改版本统一保存在需求工作区，可搜索、恢复和持续迭代。

### 三、技术架构

本项目的技术核心不是“调用一个 Agent 修改页面”，而是建立了一条面向 UI 需求示意的受控生成链路：

完整处理链路包括：

1. 捕获运行态页面状态并进行安全裁剪；
2. 生成可维护的静态源码与语义索引；
3. 结合对话和页面状态判断普通问答、页面修改或关键歧义；
4. 构建渐进式上下文并声明结构化修改意图；
5. 由受控源码 Agent 理解需求并选择工具；
6. 执行原子化 HTML/CSS 修改；
7. 完成空间范围、安全性、结构和可预览性校验；
8. 通过 Revision 事务提交结果并形成交付物。

其中，模型专注于理解需求和选择下一步工具；页面快照、源码结构、操作权限、校验规则、版本提交和回滚由系统确定性控制，形成兼具自然语言理解能力与工程可控性的页面生成体系。

**1. 七项关键技术能力**

1. **语义意图路由。** 同一对话入口统一承接方案咨询、需求澄清和页面修改。系统结合用户输入、最近对话、页面工作区和选区状态选择对应处理链路，页面编辑能力仅在明确的修改任务中开放。
2. **运行态页面编译。** 将浏览器中已经渲染的页面转换为可维护的 HTML、CSS、Outline 和 Source Map，同时冻结表单值、弹窗和可见样式，为后续编辑保留完整页面状态。
3. **渐进式上下文。** 先向 Agent 提供页面结构摘要和选区，再根据任务按需搜索元素、读取局部源码和完整样式规则，以更精确的页面上下文支撑复杂修改。
4. **受控源码协议。** 将意图声明、读取、替换、插入、删除、移动、克隆、重排、校验和提交封装为边界明确的工具；多个相关操作支持原子执行，任一环节未通过校验均保持原版本不变。
5. **语义空间约束。** 以选区和最近语义容器作为默认锚点，理解“右侧、下方、附近”等自然位置描述，并对新增模块执行空间归属和可见性校验。
6. **Revision 事务模型。** 所有修改先在 Working Copy 中执行，校验通过后形成 Revision；每个有效版本均可撤销、重做和恢复，版本切换时同步保持对话上下文一致。
7. **可观测评测闭环。** 完整记录模型调用、工具调用、耗时、源码操作和校验结果，并通过固定回归集、挑战集和真实案例持续评估页面编辑质量。

这七项能力共同构成了“理解需求—澄清歧义—受控修改—验证结果—提交版本”的工程闭环，也是本项目区别于通用网页聊天机器人或简单 DOM 修改脚本的关键。

**2. 为什么采用通用源码 Agent**

静态副本本质上是一组 HTML/CSS 文件，项目以 Cline SDK 承载上下文管理、Agent Loop、记忆和工具调度等通用能力，并通过 Adapter 将 UI 需求理解、页面语义、源码工具和安全策略接入统一执行链路。

Adapter 负责注入当前工作区、选区、对话分支和文件工具，并持续采集源码操作与校验结果；项目业务层负责定义 Agent 的读取范围、编辑权限、回滚条件和版本提交标准。当前静态源码编辑链路统一使用 Cline SDK，模型调用层保持可替换，现已接入 DeepSeek。

**3. 通用层与业务层分工**

- **通用 Agent Runtime：** 负责模型调用、上下文管理、循环执行、工具调度、错误处理和收敛控制，优先复用 Cline SDK、Vercel AI SDK 等成熟能力。
- **助手意图层：** 负责普通问答、页面修改和关键歧义的语义路由，普通问答与页面编辑使用不同的权限边界。
- **UI 源码业务层：** 负责页面语义、选区锚点、结构化修改意图以及样式和结构约束，由项目结合业务场景建设。
- **受控工具层：** 提供搜索、局部读取、样式读取、移动、克隆、Patch 和校验等能力，由项目建设并严格限制操作范围。
- **工作区层：** 负责源码文件、Revision、撤销重做、历史副本管理和静态预览，由项目建设。
- **安全层：** 负责页面裁剪、安装身份、用户与租户隔离、路径隔离、CSP、敏感信息和危险内容校验，由项目建设。

**4. 受控源码工具**

Agent 可使用的主要能力包括：

- 页面 Outline 和元素检索；
- 按 sourceId 检查元素；
- 局部读取 HTML/CSS；
- 一次读取完整样式规则；
- 移动已有结构；
- 克隆已有结构并保留样式；
- 精确文本替换；
- 受控 Patch；
- HTML/CSS 和安全校验；
- 新增元素空间范围校验；
- 提交、完成或请求用户澄清。

Agent 不能访问 Shell、任意网络、浏览器控制能力、其他目录或其他用户工作区。

**5. 分层技术架构**

1. **插件交互层**：WXT、React、Chrome MV3 Side Panel。
2. **快照捕获层**：读取运行态页面、表单状态、弹窗和计算样式。
3. **快照编译层**：安全裁剪、HTML 格式化、CSS 去重、Outline 和 Source Map。
4. **Agent Service**：Hono HTTP 服务、语义意图路由、普通问答、DeepSeek 模型调用和 Cline Adapter。
5. **源码编辑层**：通用 Agent 和受控源码工具。
6. **工作区层**：文件、Revision、撤销重做、历史副本管理与静态预览。
7. **安全层**：安装身份、用户与租户隔离、路径隔离、危险内容校验、CSP 和体积限制。
8. **可观测与评测层**：JSONL 日志、实时进度、Vitest 和挑战场景评测。

**6. 安全设计**

安全是企业级 AI 工具能否推广的前提。本项目从授权、页面、身份与资源、源码工作区、预览、版本和可追溯七个维度构建安全防线。

**（1）最小授权：** 插件采用 activeTab 临时授权，不申请 all_urls 长期权限，仅处理用户主动打开并授权的普通 HTTP/HTTPS 页面。

**（2）页面主动去能力：** 捕获阶段移除 script、iframe、on* 事件、表单 action、外链资源、React/Vue 运行时标记、Cookie、LocalStorage 等。

**（3）身份与资源隔离：** 面向内部试点，插件首次连接服务时自动获得独立安装身份，无需用户额外注册账号或配置数据库。页面副本、修改记录、Revision、历史工作区和回收站均按照用户与租户隔离，预览链接使用工作区级授权。

**（4）源码工作区隔离：** Agent 只能访问当前 Workspace 中允许编辑的源码文件，所有路径经过 realpath 校验，禁止通过上级目录逃逸或符号链接攻击。

**（5）预览隔离：** 静态副本通过 CSP 禁止脚本、接口、表单提交和页面导航，确保示意页不能转化为真实业务操作工具。

**（6）版本与恢复：** 每次成功修改形成一个 Revision。校验失败不提交；撤销后对应无效分支的对话上下文也会被截断。

**（7）可追溯：** 日志记录用户指令、Agent 操作摘要、工具结果、校验状态、Revision、模型/工具调用次数和耗时，并对敏感字段脱敏。

**当前安全边界：** 目前已实现安装级身份和用户工作区隔离，适用于公司内网受控试点；正式规模化推广前仍需接入公司统一身份认证，并补充自动过期清理、限流和更细粒度的日志访问权限。

## 发展规划

本项目的长期目标不是增加更多孤立的 UI 操作，而是逐步改变企业内部“需求如何被表达、评审和实现”的方式：

**发展愿景：从一个帮助产品经理快速生成页面改动示意的工具，发展为连接产品、设计、研发和测试的 AI UI 需求协同平台。**

### 一、第一阶段：内部推广（0～3 个月）

**目标**：验证并复制需求可视化价值，形成可复制的推广模式。

**关键动作**：

- 选择 1～2 个低风险、已脱敏的内部系统作为试点；
- 面向产品经理和交互设计同学开展小范围试用，覆盖新增字段、筛选项、按钮、表格、弹窗、状态和布局调整等高频需求；
- 建立“需求描述—页面示意—研发反馈—结果修正”的闭环记录；
- 沉淀适合内部业务的使用方法、示例库和场景模板。

### 二、第二阶段：流程接入（3～6 个月）

**目标**：将 UI 示意从个人工具升级为需求评审流程中的标准环节。

**关键动作**：

- 接入公司现有需求平台，使指令、选区、示意截图、Revision 和评审意见直接关联到需求条目；
- 产品经理在需求上下文中创建和调整示意，研发和设计人员在同一条需求下查看修改前后结果；
- 沉淀结构化 UI 变更说明、页面状态清单和评审结论；
- 保留需求从提出、修改到确认的完整版本轨迹。

### 三、第三阶段：能力升级（6～12 个月）

**目标**：从局部示意走向页面体验重构，形成企业级 AI UI 协同能力。

**关键动作**：

- 沉淀企业组件、视觉规范和业务页面模式，使 AI 能够识别并遵循公司 UI 规范；
- 能力范围从单个区域扩展到页面级信息架构、模块重排、多状态方案、不同角色视图；
- 支持多个页面方案对比，帮助产品经理在需求早期识别遗漏状态和体验问题；
- 最终形成覆盖“需求描述—方案生成—评审确认—研发理解—测试验收”的全链路协同。

## 核心创新与竞争优势

本项目将真实业务页面、自然语言交互和受控页面生成结合起来，形成三项核心优势：

**1. 真实页面即需求画布。** 产品经理直接在现有页面副本中选定区域并描述改动，无需重新搭建原型；生成结果自然保留原页面的结构、样式和业务上下文。

**2. AI 直接生成共同视觉结果。** AI 理解需求意图并完成页面调整，支持连续对话、撤销和重做，使产品、设计、研发和测试能够围绕同一个可视化结果评审和确认。

**3. 企业级可控与持续沉淀。** 页面编辑在隔离环境中受控执行，不影响真实业务；页面状态、对话和修改版本沉淀为可管理的需求工作区，可进一步连接企业需求平台和协作流程。
